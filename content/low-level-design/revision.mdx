## Guide

**[The LLD Interview Framework](./interview-framework.mdx)**

- **6 steps:** Requirements → Core classes → Class diagram → Main methods → Code → Edge cases and extensions.
- **Requirements first:** features, out of scope, and your assumptions, said out loud.
- **Nouns → classes, verbs → methods, fixed choices → enums.**
- **One job per class.** A new feature should be a new class, not an edit to an old one.
- **Code the main flow first**, then cover wrong input, two requests at once, and the patterns that help it grow.

## 1. OOP Basics

**[Classes and Objects](./oop-basics/classes-and-objects.mdx)**

- A **class** is the blueprint; an **object** is one thing made from it with `new`.
- The **constructor** sets the starting values. `this` is the current object.
- Methods are shared by all objects; each object keeps its own data.
- **Static** members belong to the class, not to any object: `Math.max`, `Date.now`.
- The four pillars: encapsulation, abstraction, inheritance, polymorphism.

**[Encapsulation](./oop-basics/encapsulation.mdx)**

- **Encapsulation:** keep data inside the object; change it only through methods that keep the rules.
- `#field` is truly private. `_field` is only a naming habit.
- JavaScript has **no protected**. A child class can't read the parent's `#` fields; it uses the parent's methods.
- **Getters and setters** control how a property is read and changed.
- `obj.#field` outside the class is a SyntaxError that stops the **whole file**.

**[Abstraction](./oop-basics/abstraction.mdx)**

- **Abstraction:** show what it does, hide how it does it.
- Give a class a few simple public methods; keep the inside steps private.
- An **interface** is abstraction at the design level: callers depend on "can pay", not on "card".
- Abstraction hides **complexity**; encapsulation hides and guards **data**.
- Good abstraction lets you change the inside without changing the callers.

**[Inheritance](./oop-basics/inheritance.mdx)**

- `class Child extends Parent`: the child gets the parent's properties and methods, and can add or override.
- `super(...)` runs the parent's constructor and must come **before** any `this`. `super.method()` calls the parent's version.
- No constructor in the child? JavaScript passes all arguments to the parent for you.
- Use inheritance only for a true **"is-a"**, and keep trees shallow.
- Parent changes can break children (fragile base class). When in doubt, prefer composition.

**[Polymorphism](./oop-basics/polymorphism.mdx)**

- **Polymorphism:** one call, and each object does it its own way.
- **Overriding:** a child redefines a parent's method. This is the main kind in JavaScript.
- Call `shape.area()` without knowing the shape. No `if`/`else` on types.
- **Duck typing:** in JavaScript, any object with the method works.
- **No overloading** in JavaScript: one method that checks its arguments, or default values.

**[Interfaces and Abstract Classes in JavaScript](./oop-basics/interfaces-abstract-classes.mdx)**

- **Interface:** a promise of methods, no code. In JavaScript: a base class marked `// interface` whose methods throw.
- **Abstract class:** shared code plus methods to fill in; can't be created. In JavaScript: a `new.target` check in the constructor.
- Interface = a role ("can pay"). Abstract class = a family that shares code ("is a vehicle").
- In diagrams: `<|..` dashed for implements, `<|--` solid for extends.
- Duck typing also works in JavaScript; the base class adds a name and clear errors.

**[Composition vs Inheritance](./oop-basics/composition-vs-inheritance.mdx)**

- **Inheritance = is-a. Composition = has-a.**
- Composition builds an object from small parts that can be swapped, even while the program runs.
- Inheritance trees grow fast: every mix needs a class, and parent changes break children.
- **"Favor composition over inheritance"**: prefer it, but inheritance is fine for a true, shallow is-a.
- A swappable part behind an interface, like `FlyBehavior`, is the **Strategy** pattern.

## 2. Design Principles

**[Single Responsibility Principle](./design-principles/single-responsibility.mdx)**

- **One class, one job.** One job = one reason to change.
- Ask "**who** would ask me to change this?" Different people means different classes.
- The "**and**" test: if you need "and" to describe a class, it may do too much.
- It is not "one method per class". Group by reason to change.
- A classic split: **data and rules** / **formatting** / **saving**.

**[Open/Closed Principle](./design-principles/open-closed.mdx)**

- **Add new code, don't edit old code.**
- Open for **extension**, closed for **modification**.
- The tool: an **interface** plus one class per kind ([Strategy](./design-patterns/strategy.mdx)).
- The smell: a growing `if/else` or `switch` on a type.
- Keep the "which class?" choice in **one** place, like a factory.

**[Liskov Substitution Principle](./design-principles/liskov-substitution.mdx)**

- **A child keeps the parent's promises.** Swap in any subclass and the code still works.
- "Is-a" in real life is not enough. Ask "does it **behave** like one?"
- Classic breaks: **Square extends Rectangle**, **Penguin extends Bird**.
- Smells: a child that **throws**, does **nothing**, or callers that use **`instanceof`**.
- Fix: a smaller parent or interface that **every** child can honour.

**[Interface Segregation Principle](./design-principles/interface-segregation.mdx)**

- **Small interfaces. Only promise what you can do.**
- No class should be forced to have methods it can't use.
- The smell: methods that **throw "not supported"** or are **empty**.
- Split by **role** (who uses it), not one interface per method.
- Callers should ask for the **small role** they need, like `Printer`, not the whole `Machine`.

**[Dependency Inversion Principle](./design-principles/dependency-inversion.mdx)**

- **Depend on the socket, not the power station.**
- High-level code (the rule) and low-level code (the detail) both depend on an **interface**.
- The interface is shaped by the **rule's** needs: `send(customer, text)`, not `sendEmail()`.
- The smell: `new SomeDatabase()` or an outside SDK inside business code.
- **Inversion** = what to depend on. **Injection** = how it gets passed in.

**[DRY, KISS and YAGNI](./design-principles/dry-kiss-yagni.mdx)**

- **Say it once. Keep it plain. Build it when it's needed.**
- **DRY** is about **knowledge**, not text. Code that changes for different reasons is not a copy.
- **Rule of three:** merge copies on the third time, not the first.
- **KISS:** easy to read beats clever. Few classes beat many patterns.
- **YAGNI:** mention extras as extensions; don't build them.

**[Coupling and Cohesion](./design-principles/coupling-cohesion.mdx)**

- **Tight inside, loose between.**
- **Coupling** = how much classes depend on each other. Keep it **low**.
- **Cohesion** = how well a class's parts belong together. Keep it **high**.
- Smell of tight coupling: long chains like `a.b.c.d()`. Talk only to your direct neighbours.
- Smell of low cohesion: methods that use **different** fields, and `Utils` classes.

**[Dependency Injection](./design-principles/dependency-injection.mdx)**

- **Don't build it, receive it.** Dependencies come in from outside.
- **Constructor injection** is the default.
- The big win: tests can pass **fakes**. No network, no real money.
- Create the real objects in **one place**, at program start (the composition root).
- **Injection** = how it arrives. **Inversion** = depend on an interface. **IoC** = a framework calls your code; DI is one kind of it.

## 3. Modeling and UML

**[Finding Classes from Requirements](./modeling-uml/finding-classes.mdx)**

- **Nouns are things, verbs are actions.** Nouns become classes or fields, verbs become methods.
- A noun is a **class** if it has its own data **and** actions. Values that describe something are **fields**.
- A **verb that leaves a record** (borrow, book, rent) becomes a class: `Loan`, `Booking`.
- Put each method on the class that **has the data** it needs.
- Split the **description** from the **item**: `Book` vs `BookCopy`.

**[Class Diagrams](./modeling-uml/class-diagrams.mdx)**

- **Name on top, data in the middle, actions at the bottom.**
- Visibility: `+` public, `-` private, `#` protected. JavaScript's `#field` is drawn as `-field`.
- Mark the kind: `<<interface>>`, `<<abstract>>`, `<<enumeration>>`, plus the colour.
- Static is underlined (`$`), abstract is in italics (`*`).
- In an interview: **key classes and main methods only**. Skip getters, setters and constructors.

**[Association, Aggregation and Composition](./modeling-uml/relationships.mdx)**

- **Does the part die with the whole?** Yes = composition (filled diamond), No = aggregation (hollow diamond).
- **Association** (`-->`) = keeps it in a field. **Dependency** (`..>`) = uses it for a moment.
- **Inheritance** (`<|--`) = is a kind of. **Implements** (`<|..`) = plays an interface's role.
- The diamond sits on the **whole**. The triangle points at the **parent**.
- Multiplicity: `1`, `0..1`, `many`, `1..*`. Read each number next to its own class.

**[Sequence Diagrams](./modeling-uml/sequence-diagrams.mdx)**

- **Objects across, time down.** Each arrow is one call.
- Solid arrow = **call**, dashed arrow = **return**.
- `alt`/`else` for if/else, `opt` for "if", `loop` for repeats.
- Draw **one main flow**, with **five participants or fewer** and short method names.
- Great for showing **two requests at once** and where they clash.

## 4. Design Patterns

**[Singleton](./design-patterns/singleton.mdx)**

- A Singleton is **one object** for the whole app, reached in **one way**.
- In JavaScript, **export one instance from a module**. The textbook form is a static `getInstance()` with a private constructor.
- Fine for **config, a logger, a connection pool**. Not fine as a lazy way to share changing data.
- Its costs are **hidden global state** and **hard tests**. Create one object and **pass it in**.
- For async setup, store the **promise**, not the result.

**[Factory](./design-patterns/factory.mdx)**

- A Factory **creates objects for you**, so callers ask for "what" and never name the class.
- **Simple Factory:** one function with a lookup table. In JavaScript, a `Map` from type to class.
- **Factory Method:** the base class does the shared steps, and subclasses override one "create" method.
- **Abstract Factory** makes matching families of objects. Rare in interviews.
- Everything a factory returns shares **one interface**, so adding a type doesn't change the callers.

**[Builder](./design-patterns/builder.mdx)**

- Builder creates a complex object **step by step**, then `build()` hands it over.
- Each step **returns `this`**, so calls chain: `new PizzaBuilder().size('L').cheese().build()`.
- Put the **checks in `build()`**, where all the parts are known.
- In JavaScript, an **options object** with defaults often does the job.
- Factory picks **which** class. Builder decides **how** one object is put together.

**[Adapter](./design-patterns/adapter.mdx)**

- An Adapter is a **travel plug** for code: it makes the wrong interface fit the one you use.
- Roles: **target** (your interface), **adaptee** (their class), **adapter** (the translator).
- Wrap the object (an **object adapter**). In JavaScript it can also be a function, like `util.promisify`.
- Put every outside system behind **your own interface**, with **one adapter per provider**.
- Adapter fits **one** thing to an existing interface. Facade makes a **new, simpler** front for many.

**[Decorator](./design-patterns/decorator.mdx)**

- A Decorator **wraps** an object with the **same interface**, and adds a bit of behavior.
- A decorator **is a** component and **has a** component, so wrappers can stack.
- It replaces a **subclass for every mix** with one small class per extra.
- In JavaScript, a function that wraps a function (`withLogging(fn)`) is a decorator too.
- Decorator **adds behavior**. Proxy **controls access**. Same shape, different purpose.

**[Facade](./design-patterns/facade.mdx)**

- A Facade is a **front desk**: one simple class in front of many.
- It knows **which classes to call, and in what order**, including undo on failure.
- It **coordinates**. The business rules stay in the classes behind it.
- It is a **shortcut, not a wall**. Advanced code can still reach the classes inside.
- Facade makes a **new, simpler** front for many. Adapter makes **one** thing fit an existing interface.

**[Proxy](./design-patterns/proxy.mdx)**

- A Proxy is a **stand-in** with the **same interface** that controls access to the real object.
- Main kinds: **lazy** (create when needed), **caching**, **protection** (access checks), **remote**.
- JavaScript has a built-in **`Proxy`** with traps like `get` and `set`.
- Proxy **controls access**. Decorator **adds behavior**. Same shape, different purpose.
- Caching proxies need an **expiry rule**, or they serve old data.

**[Composite](./design-patterns/composite.mdx)**

- Composite builds **trees** where a group and a single item share **one interface**.
- Roles: **component** (the interface), **leaf** (`File`), **composite** (`Folder`, which holds components).
- A composite's method **asks each child and combines** the answers, like `size()` adding up.
- No "is it a file or a folder?" checks in callers. A new item type is **one new class**.
- Watch for **cycles**: a folder must never end up inside itself.

**[Strategy](./design-patterns/strategy.mdx)**

- **Strategy = snap-in blades.** One interface, many ways to do the job; the context holds one and calls it.
- It replaces a growing **if/else on a type** with one class (or function) per rule.
- In JavaScript, a one-method strategy can be **just a function**, like the compare function in `sort`.
- Choose the strategy in **one place**: the constructor, a factory or a lookup table.
- Strategy vs [State](./design-patterns/state.mdx): the **caller** picks a strategy; a state object **switches itself**.

**[Observer](./design-patterns/observer.mdx)**

- **Observer = subscribe to a channel.** The subject keeps a list; observers subscribe, unsubscribe and get `update` calls.
- The subject **doesn't know** who listens, so you add listeners without editing it.
- In JavaScript: callbacks, `EventEmitter` (`on`, `off`, `emit`) and `addEventListener`.
- **Always unsubscribe**, and don't let one slow or failing observer block the rest.
- Between services, it becomes **pub/sub** with a broker in the middle.

**[Command](./design-patterns/command.mdx)**

- **Command = an order slip.** A request turned into an object, usually with `execute()` and `undo()`.
- The **invoker** (editor, remote, queue) runs commands without knowing what they do.
- Undo and redo = **two stacks** of commands; a new action clears the redo stack.
- Each command **saves what it needs** to undo itself.
- Also great for **queues, logs, retries and macros**.

**[State](./design-patterns/state.mdx)**

- **State = a toy with modes.** One class per mode; the context forwards every action to its current state.
- The **states choose the next state** through `setState`.
- A base state with **"not now" defaults** means each state writes only what it allows.
- Strategy vs State: the **caller** picks a strategy; a state **switches itself**.
- For small machines, an **enum plus a transition table** is enough.

**[Template Method](./design-patterns/template-method.mdx)**

- **Template Method = one recipe card.** The base class fixes the steps in `run()`; subclasses fill in the steps that change.
- Steps can be **abstract** (must fill in), **default** (may replace) or a **hook** (empty, optional).
- Never override the template method. JavaScript has no `final`, so **say it in a comment**.
- Don't use `#private` for steps: subclasses can't override them.
- Inheritance suits a **fixed flow**; use Strategy (functions) when steps must be **swapped or mixed**.

**[Chain of Responsibility](./design-patterns/chain-of-responsibility.mdx)**

- **Chain of Responsibility = the support desk.** Handlers stand in a line; each handles the request or passes it on.
- The sender knows only the **first handler**; the chain is built outside and easy to reorder.
- Two forms: **"the first one that can"** (support desk) and **"every step, any can stop"** (middleware).
- Always **end the chain** with a clear answer, and never forget `next()`.
- Seen in **Express middleware**, **DOM event bubbling**, ATM cash dispensers and log levels.

## 5. Concurrency in LLD

**[Concurrency in JavaScript](./concurrency/concurrency-in-javascript.mdx)**

- **One waiter, many tables:** one thread plus the event loop. One task runs at a time, to the end.
- **Concurrency** is taking turns; **parallelism** is the same instant. The main thread is concurrent, not parallel.
- `await` pauses the function, not the thread. Other code runs **only at an `await`**.
- CPU-heavy work blocks everyone: move it to a **worker thread**.
- Java threads can be paused **at any line**, which is why Java talks so much about locks.

**[Race Conditions and Locks](./concurrency/race-conditions-locks.mdx)**

- A **race** is when the result depends on timing. The danger shape is **check, `await`, write**.
- **Fix 1:** check and write with **no `await` between** them (atomic).
- **Fix 2:** a **mutex** around the critical section, released in `finally`.
- **Fix 3:** many servers? A **database rule**: a conditional update or a unique index.
- **Deadlock:** lock in the same order, hold locks briefly, use timeouts.

**[Making a Design Thread-Safe](./concurrency/thread-safe-design.mdx)**

- First **find the shared state that changes**; everything else is already safe.
- Prefer, in order: **don't share, don't change, atomic step, lock, database rule**.
- Lock rules: **per object**, **small critical sections**, **the same order** everywhere.
- In Node, the danger is only at an `await`; in Java, it is at **any line**.
- With many servers, the **database is the real guard**.

**[Producer-Consumer](./concurrency/producer-consumer.mdx)**

- **Producer-Consumer = the bakery rack.** Producers add, consumers take, and a queue sits between them so each side works at its own speed.
- **Bound the queue**, and decide what happens when it is full: wait (backpressure), drop or reject.
- In JavaScript: `put` awaits while full, `take` awaits while empty, and each **checks again in a `while`** after waking up.
- Stop consumers with **one stop signal per consumer**.
- Across services it becomes a **message broker**: acknowledge after the work, and make handlers idempotent.

## 6. Practice Problems

**[Design a Parking Lot](./problems/parking-lot.mdx)**

- Ask about sizes, fees and gates first. Say that payment and booking are out of scope.
- A vehicle knows its size, and a spot knows if a vehicle fits. No `if (type === 'TRUCK')` in the lot.
- The fee and the spot choice are Strategies: a new rule is a new class.
- Find and take a spot with no `await` in between. With many servers, let the database pick the winner.
- Pass the lot to the gates. It doesn't need to be a Singleton.

**[Design a Vending Machine](./problems/vending-machine.mdx)**

- The same button does different things in different states. That is the State pattern.
- Four states: Idle, HasMoney, Dispensing, OutOfStock. Draw the moves between them first.
- The base state refuses everything. Each state allows only what makes sense.
- Paying and making change is all or nothing. If change is impossible, refuse the sale and keep the money separate.
- Switch to `Dispensing` before any `await`, so a second press is refused.

**[Design Tic-Tac-Toe](./problems/tic-tac-toe.mdx)**

- `Board` stores cells, `WinChecker` knows the rule, `Game` runs the turns. One job each.
- O(1) win check: a counter per row, column and diagonal. X adds 1, O adds -1. N or -N means a win.
- Check for a win before you check for a draw.
- `Player` is an interface, so people and bots plug in the same way.
- A bad move throws, and the same player tries again.

**[Design an LRU Cache](./problems/lru-cache.mdx)**

- Map for "find it in O(1)", doubly linked list for "move or remove it in O(1)".
- The node keeps its key, so an evicted node can be deleted from the Map.
- Fake `head` and `tail` nodes remove every `null` check.
- The `Map` shortcut (delete, then set) is fine for small caches. It is not a sure O(1): in V8, `keys().next()` slows down after many deletes. Offer it, then write the long way.
- `get` changes the order too, so in Java even reads need the lock.

**[Design a Logger](./problems/logger.mdx)**

- Drop low levels first. A filtered log should cost almost nothing.
- The logger tells every appender (Observer). Where a line goes and how it looks are separate (Appender and Formatter).
- Write files in the background with one writer and a buffer, so logging never slows a request.
- Make one logger at startup and pass it in. A Singleton is easy to reach, but hard to test.
- A broken output must never break the app.

**[Design an Elevator System](./problems/elevator.mdx)**

- Hall button = "choose a car for me". Car button = "this car, take me there".
- The controller picks **which** car (Strategy). The car picks the **order** of its stops (LOOK).
- Car states are classes: Idle, MovingUp, MovingDown, DoorsOpen. `tick()` asks the current state what to do.
- "Nearest car" can pick a car that is going away. Count the steps until it really reaches you.
- Use `tick()` instead of real time, so the design is easy to test.

**[Design a Library Management System](./problems/library-management.mdx)**

- `Book` is the title. `BookCopy` is the real object on the shelf. You borrow a copy and reserve a title.
- The member checks its own limits: 3 books, no unpaid fines.
- A returned copy goes to the first person in line (ON_HOLD), and they are told: Observer.
- Pass the clock in. Then a "17 days later" test takes one line.
- Check and take the last copy with no `await` in between. With many servers, use a conditional `UPDATE`.

**[Design Snake and Ladder](./problems/snake-and-ladder.mdx)**

- `Snake` and `Ladder` are both a `Jump`: land on `from`, go to `to`. The game never asks which one it is.
- Pass the dice in. `FixedDice` makes every test game the same.
- The "past 100" check is a `MoveRule`. A home rule is a new class.
- Check the board when it is built: snakes go down, ladders go up, one jump per cell, no chains.
- One turn = one method with no `await` inside. Online, also check whose turn it is.

**[Design an ATM](./problems/atm.mdx)**

- The steps are states: Idle → CardInserted → Authenticated. The base state says "not now" to every button.
- The ATM never stores balances or PINs. It asks the bank through a `Bank` interface.
- Notes come from a chain: ₹500 → ₹200 → ₹100. Each gives what it can and passes the rest on.
- Check the notes first, then debit, then dispense. If the cash fails, reverse the transaction.
- One account, two ATMs: the bank must check and take the money in one step.

**[Design Splitwise](./problems/splitwise.mdx)**

- Money is whole paise (or cents), never a decimal number. `0.1 + 0.2` is not `0.3`.
- Each split type is a Strategy. Every split must add up to the total; left-over paise go to the first people.
- Keep one net balance per person: above 0 gets money back, below 0 owes.
- Simplify greedily: the biggest debtor pays the biggest creditor, again and again.
- Add an expense in one step: no `await` in the middle, or one database transaction.

**[Design a Rate Limiter](./problems/rate-limiter.mdx)**

- Ask: who is limited, how a limit is written, and are bursts OK?
- The algorithm is a Strategy. A factory makes it from a rule, so a config change swaps it.
- Token bucket: 2 numbers, allows bursts. Sliding window: one timestamp per request, strict.
- No timer refills the bucket. Each call works out the tokens earned since the last one.
- One process is safe with no `await`. Many servers need one shared store, like Redis, with atomic updates.

**[Design an In-Memory Key-Value Store](./problems/key-value-store.mdx)**

- Build it in steps: a Map, then TTL, then transactions. Each step adds code and doesn't rewrite the last one.
- TTL: save `expiresAt`. Delete lazily when read, and with a periodic job for keys nobody reads.
- Transactions are a stack. Each one stores only its changes, and `null` means "deleted".
- `get` checks the newest transaction first. `commit` moves changes one level down. `rollback` just pops.
- Pass the clock in, so TTL tests run at once.

**[Design a Pub-Sub System](./problems/pub-sub.mdx)**

- The broker sits in the middle. Publishers and subscribers never know each other.
- A topic keeps its messages in order. Each subscriber keeps its own offset, like a bookmark.
- One delivery loop per subscriber. A slow one falls behind, but never blocks the publisher or the others.
- Retry a failing message a few times, then put it in the dead letters and move on.
- Pick a rule for slow subscribers: keep everything, a retention limit, drop, or back-pressure.

**[Design a Task Scheduler](./problems/task-scheduler.mdx)**

- Keep the waiting tasks in a min-heap by run time: see the next in O(1), add and take out in O(log n).
- One timer, set for the task on top. Reset it when an earlier task arrives or a run ends.
- Cancel = mark it and skip it later (lazy delete).
- Recurring = put the task back after each run. Retry = put it back later, and double the wait each time.
- Count the slot before any `await`. At most `maxConcurrent` tasks run at once.

**[Design a Movie Ticket Booking System](./problems/movie-ticket-booking.mdx)**

- **Hold first, pay second.** A hold has an end time, and an old hold counts as free.
- `holdSeats` is **all or nothing**, with **no `await`** between the check and the write.
- Before an `await`, mark the booking (`PAYING`). After it, **check again** before you write.
- Seat state lives in **`Show`**, because one seat has a different state at every show.
- Many servers: let the **database** decide with one conditional update. Pricing is a **Strategy**.

**[Design a Hotel Booking System](./problems/hotel-booking.mdx)**

- A stay is a **range of nights**: check-in day included, check-out day not.
- Two stays clash if `a.start < b.end && b.start < a.end`. Back-to-back is fine.
- Put the overlap rule in a small **`DateRange`** class, and let each **`Room`** check its own bookings.
- **Refund rules are a Strategy**, chosen and stored per booking.
- `book` searches and saves **in one call with no `await`**. Many servers: the database refuses clashes.

**[Design a Ride-Sharing App](./problems/ride-sharing.mdx)**

- A ride is a **state machine**: `REQUESTED → ACCEPTED → STARTED → COMPLETED`, or `CANCELLED` before the start.
  Keep the allowed moves in **one table** inside `Ride`.
- **Matching and fare are Strategies.** Surge is just a different fare strategy.
- **Notifications are Observers.** New messages mean new listeners, not new `if`s.
- `acceptRide` checks the driver and the ride, then writes both, with **no `await`** in between.
- Many servers: a **conditional update** (`WHERE status = 'AVAILABLE'`) decides who wins.

**[Design Chess](./problems/chess.mdx)**

- **Ask each piece** `canMove`. An abstract `Piece` and six subclasses: no `if (piece is a knight)`.
- Rook, bishop and queen also need **`isPathClear`**. The knight jumps.
- **Check:** can any enemy piece reach my king? **Legal move:** do it, check, undo if needed.
- **Checkmate:** in check and no legal move. **Stalemate:** no legal move and not in check.
- **`Move` is a Command** with `undo`. It remembers the captured piece.

**[Design an In-Memory File System](./problems/in-memory-file-system.mdx)**

- **Composite:** an abstract `Entry`, a `File` leaf, and a `Directory` holding more entries.
- A folder's **size is the sum of its children**: one line of recursion.
- **Parse paths once** (`/a//b/` gives `a`, `b`) and walk from the root with a `Map` lookup per name.
- Clear errors: `ENOENT` (missing), `ENOTDIR` (file used as a folder), `EISDIR` (folder used as a file), and never
  delete `/`.
- **Permissions:** a Proxy in front. **Symlinks:** a new `Entry` subclass with a hop limit.
