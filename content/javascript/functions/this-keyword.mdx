## The idea

`this` is a special word inside a function. It points to an **object**. Which object? That is decided **when the function is called**, not where it is written.

Think of the word **"me"**. The sentence "Give the book to me" is always the same, but who "me" is depends on **who says it**. A function is the sentence. The way it's called decides who `this` is.

The quick rule: **look at what is left of the dot when the function is called.** In `user.greet()`, `this` is `user`. The rest of this page covers the cases where there is no dot, or where something else wins.

## The four rules

| Rule | How the function is called | What `this` is |
| --- | --- | --- |
| **1. Default** | A plain call: `greet()` | The global object, or `undefined` in strict mode |
| **2. Implicit** | As a method: `user.greet()` | The object before the dot: `user` |
| **3. Explicit** | With `call`, `apply` or `bind`: `greet.call(admin)` | The object you pass in: `admin` |
| **4. new** | With `new`: `new Person()` | The brand-new object being made |
| **Arrow functions** | Any way at all | Not their own: the `this` of the code around them |

When more than one rule could apply, the stronger one wins: **new**, then **explicit**, then **implicit**, then **default**. Arrow functions ignore all four.

So, to find `this`, ask these questions **in order** and stop at the first "yes":

1. Is it an **arrow function**? Then `this` is the `this` of the code around it.
2. Was it called with **`new`**? Then `this` is the new object.
3. Was it called with **`call`, `apply` or `bind`**? Then `this` is the object passed in.
4. Was it called as **`obj.method()`**? Then `this` is `obj`.
5. None of these? `undefined` in strict mode, otherwise the global object.

### 1. Default binding: a plain call

When you call a function on its own, with nothing before it, `this` is the **global object**. `globalThis` is the name for it everywhere (in browsers it's `window`, in Node it's `global`).

```js
function showThis() {
    console.log(this === globalThis);
}

showThis(); // true
```

In **strict mode**, a plain call gives `undefined` instead. Strict mode is a safer version of JavaScript. You turn it on with `"use strict"`, and it's always on inside **classes** and **ES modules**.

```js
function showThisStrict() {
    "use strict";
    console.log(this);
}

showThisStrict(); // undefined
```

### 2. Implicit binding: a method call

When you call a function as `object.method()`, `this` is the **object before the dot**.

```js
const user = {
    firstName: "Asha",

    greet() {
        console.log("Hi, I am " + this.firstName);
    },
};

user.greet(); // Hi, I am Asha
```

The same function gives a different `this` depending on which object calls it:

```js
function introduce() {
    console.log("I am " + this.firstName);
}

const asha = { firstName: "Asha", introduce: introduce };
const ravi = { firstName: "Ravi", introduce: introduce };

asha.introduce(); // I am Asha
ravi.introduce(); // I am Ravi
```

With a chain like `company.team.lead.greet()`, only the **last** object before the dot counts: `this` is `lead`.

### 3. Explicit binding: call, apply and bind

These three let **you** choose `this`. `call` and `apply` run the function now. `bind` gives back a new function with `this` fixed forever.

```js
function introduce(city) {
    console.log(this.firstName + " from " + city);
}

const asha = { firstName: "Asha" };

introduce.call(asha, "Pune"); // Asha from Pune
introduce.apply(asha, ["Pune"]); // Asha from Pune

const introduceAsha = introduce.bind(asha);
introduceAsha("Delhi"); // Asha from Delhi
```

The details are in [call, apply and bind](./call-apply-bind.mdx).

### 4. new binding

`new` creates an empty object, sets `this` to it, runs the function, and gives the object back. See [Constructor Functions and new](../oop/constructor-functions-and-new.mdx).

```js
function Person(name) {
    // new made an empty object, and this points to it.
    this.name = name;
}

const asha = new Person("Asha");
console.log(asha.name); // Asha
```

### Which rule wins?

`bind` is stronger than a method call and stronger than `call`. Once a function is bound, its `this` never changes.

```js
function showName() {
    console.log(this.firstName);
}

const asha = { firstName: "Asha" };
const ravi = { firstName: "Ravi" };

const boundToAsha = showName.bind(asha);

// Explicit binding beats implicit binding.
ravi.show = boundToAsha;
ravi.show(); // Asha

// call can't change a bound function either.
boundToAsha.call(ravi); // Asha
```

## Arrow functions and this

An arrow function has **no `this` of its own**. It uses the `this` of the code **around it**, where it is written. People call this **lexical `this`**.

That makes arrows a **bad choice for object methods**:

```js
const user = {
    firstName: "Asha",

    greetArrow: () => {
        // The code around this arrow is the top level, not user.
        console.log("Hi, " + this.firstName);
    },
};

user.greetArrow(); // Hi, undefined
```

At the top level of a normal script, `this` is the global object, which has no `firstName`. In an ES module, top-level `this` is `undefined`, so this line throws a `TypeError` instead.

But it makes them **perfect for callbacks inside a method**. The arrow uses the method's `this`, which is the object:

```js
const user = {
    firstName: "Asha",
    friends: ["Ravi", "Meena"],

    showFriends() {
        // The arrow uses this from showFriends, which is user.
        this.friends.forEach((friend) => {
            console.log(this.firstName + " knows " + friend);
        });
    },
};

user.showFriends();
// Asha knows Ravi
// Asha knows Meena
```

With a regular `function` as the callback, `forEach` calls it as a plain call, and `this` is no longer `user`:

```js
const user = {
    firstName: "Asha",
    friends: ["Ravi", "Meena"],

    showFriends() {
        this.friends.forEach(function (friend) {
            console.log(this.firstName + " knows " + friend);
        });
    },
};

user.showFriends();
// undefined knows Ravi
// undefined knows Meena
```

`call`, `apply` and `bind` **can't change** an arrow's `this`:

```js
const showName = () => {
    return this.firstName;
};

const asha = { firstName: "Asha" };

console.log(showName.call(asha)); // undefined
```

## Losing this in callbacks

This is the most common `this` bug. When you write `user.greet` **without calling it**, you take only the function. The link to `user` is not part of the function. It comes from the dot **at call time**, and that dot is gone.

```js
const user = {
    firstName: "Asha",

    greet() {
        console.log("Hi, " + this.firstName);
    },
};

user.greet(); // Hi, Asha

// Copy the method into a variable. Calling it is now a plain call.
const greet = user.greet;
greet(); // Hi, undefined
```

The same thing happens when you **pass a method** to `setTimeout`, `forEach` or any other function. It gets only the function, and later calls it without your object.

```js
const user = {
    firstName: "Asha",

    greet() {
        console.log("Hi, " + this.firstName);
    },
};

setTimeout(user.greet, 100); // Hi, undefined
```

### Two fixes

Wrap it in an arrow, so it's called as `user.greet()` again. Or `bind` it.

```js
const user = {
    firstName: "Asha",

    greet() {
        console.log("Hi, " + this.firstName);
    },
};

// Fix 1: the arrow calls user.greet(), with the dot.
setTimeout(() => user.greet(), 100); // Hi, Asha

// Fix 2: bind returns a function whose this is always user.
setTimeout(user.greet.bind(user), 200); // Hi, Asha
```

### A timer inside a method

The same bug, from inside a method. A regular function passed to `setTimeout` loses the method's `this`. An arrow keeps it.

```js
const timer = {
    seconds: 10,

    startRegular() {
        setTimeout(function () {
            console.log("Regular:", this.seconds);
        }, 100);
    },

    startArrow() {
        setTimeout(() => {
            console.log("Arrow:", this.seconds);
        }, 100);
    },
};

timer.startRegular(); // Regular: undefined
timer.startArrow(); // Arrow: 10
```

Before arrow functions, people wrote `const self = this;` above the callback and used `self` inside it. You'll still see this in old code.

## this in classes

Inside a class, methods work like normal methods: `this` is the object you called them on. See [Classes](../oop/classes.mdx).

One difference: class code is **always in strict mode**. So a lost `this` is `undefined`, and you get an error instead of a quiet `undefined`.

```js
class Counter {
    constructor() {
        this.count = 0;
    }

    increment() {
        this.count = this.count + 1;
        console.log(this.count);
    }
}

const counter = new Counter();
counter.increment(); // 1

const increment = counter.increment;
increment(); // TypeError: Cannot read properties of undefined (reading 'count')
```

### Fix 1: bind in the constructor

This was the standard fix in React class components: `this.handleClick = this.handleClick.bind(this);`.

```js
class Counter {
    constructor() {
        this.count = 0;
        // Replace the method with a version bound to this object.
        this.increment = this.increment.bind(this);
    }

    increment() {
        this.count = this.count + 1;
        console.log(this.count);
    }
}

const counter = new Counter();
const increment = counter.increment;
increment(); // 1
```

### Fix 2: an arrow function as a class field

A class field runs once for each new object, inside it. So the arrow's `this` is always that object.

```js
class Counter {
    count = 0;

    // An arrow in a class field: this is always this object.
    increment = () => {
        this.count = this.count + 1;
        console.log(this.count);
    };
}

const counter = new Counter();
const increment = counter.increment;
increment(); // 1
setTimeout(counter.increment, 100); // 2
```

The trade-off: a normal method is stored **once**, on the prototype, and shared by every object. An arrow field makes a **new copy for every object**. That's fine for a few objects. For thousands, it uses more memory.

Inside a **static** method, `this` is the class itself, because you call it as `ClassName.method()`.

## Common mistakes

- **Thinking `this` is where the function is written.** For regular functions, it's decided by **how** the function is called.
- **Arrow functions as object methods.** `this` is not the object.
- **Passing `obj.method` as a callback.** The object is lost. Use `() => obj.method()` or `obj.method.bind(obj)`.
- **A regular `function` callback inside a method** (in `setTimeout` or `forEach`). Use an arrow.
- **Trying to change an arrow's `this` with `call` or `bind`.** It doesn't work.
- **Thinking `this` in a nested chain is the first object.** In `company.team.greet()`, `this` is `team`.

## In the interview

- Start with the quick rule: "it depends on how the function is called".
- List the four rules in order of strength, then add arrows.
- Expect "guess the output" questions. Practice with [Output: this](../guess-the-output/output-this.mdx).

> "`this` is decided at call time, not where the function is written. There are four rules. With `new`, it's the new object. With `call`, `apply` or `bind`, it's the object I pass. When called as `obj.method()`, it's `obj`. In a plain call, it's `undefined` in strict mode, or the global object otherwise. Arrow functions are different: they don't have their own `this`, they use the `this` of the surrounding code, and you can't change it."

**Likely follow-up:** "Why does `setTimeout(user.greet, 1000)` print `undefined` for the name?"

**Answer:** "Because I passed only the function, not the object. `setTimeout` calls it later as a plain function, with no object before the dot, so `this` is not `user`. I'd fix it with an arrow, `setTimeout(() => user.greet(), 1000)`, or with `user.greet.bind(user)`."
