## The idea

To show a list, you turn an **array of data** into an **array of JSX** with `map`. Each item gets a **`key`**: a name tag that tells React **which item is which** between renders.

Think of a **coat check**. Each coat gets a numbered ticket. Coats can be moved around on the racks, and you still get your own coat back, because the ticket stays with the coat. A key is that ticket. Without it, React would have to guess by **position**.

## Rendering a list with map

```jsx
function ProductList({ products }) {
    return (
        <ul>
            {products.map((product) => (
                <li key={product.id}>
                    {product.name}: ${product.price}
                </li>
            ))}
        </ul>
    );
}
```

`map` gives back a new array of `<li>` elements, and JSX shows every item of an array. Real data usually has an **id** from the database: that id is the best key. To show only some items, `filter` first, then `map`.

## What keys are for

When a list changes, React compares the **new** list with the **old** one. It matches items by **key**:

- Same key in both lists → the same item. React keeps its DOM node and its **state**, and only updates what changed.
- A key only in the new list → a new item. React creates it.
- A key only in the old list → a removed item. React removes it, with its state.

So keys let React **move** items instead of rebuilding them, and keep each item's state **with that item**.

## Why the index is a bad key

`key={index}` works only while the list **never changes order**. Here is what goes wrong when you add an item at the top.

Each row has an input where the user typed a note. Before: "Milk" and "Eggs". Then "Bread" is added at the top.

| Row | Before | After, with `key={index}` | After, with `key={item.id}` |
| --- | --- | --- | --- |
| 1st | Milk, note "2 litres" | **Bread**, note "2 litres" ✗ | Milk, note "2 litres" ✓ |
| 2nd | Eggs, note "a dozen" | **Milk**, note "a dozen" ✗ | Eggs, note "a dozen" ✓ |
| 3rd | (none) | Eggs, empty note | Bread, empty note ✓ |

With index keys, React sees key 0 in both lists and thinks "same item, its text changed from Milk to Bread". The input's state belongs to key 0, so the note "2 litres" stays at the top, now next to Bread.

With id keys, React sees "milk" and "eggs" are still there, just moved down, and "bread" is new. Every note stays with its item.

## The rules for keys

- **Unique among siblings.** Two items in the same list can't share a key. Keys in different lists can repeat.
- **Stable.** The same item must get the same key on every render. Never `key={Math.random()}`: React would rebuild **every** item every time, and all their state is lost.
- **On the outer element of the map.** The key goes on what `map` returns, `<ProductRow key={product.id} />`, not on an element inside `ProductRow`.
- **Not a prop.** `props.key` is `undefined` inside the component. If it needs the id, pass it again: `<ProductRow key={product.id} productId={product.id} />`.

If you forget keys, React prints a warning in the console and falls back to positions, like index keys.

No id in the data? Make one **when the data is created**, for example `crypto.randomUUID()` when the user adds a todo, and store it with the item. Don't make it while rendering.

## Keys reset state

A key isn't only for lists. On **any** component, a new key tells React "this is a different component", so React throws the old one away and starts a new one with **fresh state**.

```jsx
function ChatPage({ contactId }) {
    // A new contactId means a brand-new ChatBox with an empty message box.
    return <ChatBox key={contactId} contactId={contactId} />;
}
```

Without the key, switching from Ana to Ben would keep the half-typed message meant for Ana. See [When Not to Use an Effect](../hooks/you-might-not-need-an-effect.mdx).

## Common mistakes

- **`key={index}` on a list that changes.** State ends up on the wrong items. Use an id.
- **`key={Math.random()}`.** Every item is rebuilt on every render, and all state is lost.
- **Putting the key on the wrong element**, inside the child component instead of on the element `map` returns.
- **Reading `props.key`.** It's `undefined`. Pass the id as a separate prop.
- **Making ids while rendering.** Make them once, when the item is created, and store them.

## In the interview

> "I render lists with `map`, and give each item a `key` that's unique among its siblings and stable across renders, usually the id from the data. React uses keys to match old and new items, so it can move items instead of rebuilding them, and keep each item's state with the right item. An index key breaks when items are added, removed or reordered: the state follows the position instead of the item."

**Likely follow-up:** "When is it OK to use the index as the key?"

**Answer:** "When the list is static: it never reorders, nothing is inserted or removed in the middle, and the items have no state of their own. A list of footer links, for example."

**Another follow-up:** "How can you reset a component's state when a prop changes?"

**Answer:** "Give it a `key` based on that prop, like `key={userId}`. When the key changes, React unmounts the old component and mounts a new one with fresh state. No effect needed."

<Callout title="Remember this" type="success">
  - Lists: **`array.map(item => <Row key={item.id} ... />)`**. `filter` first if needed.
  - A **key** tells React **which item is which**. Same key → keep its DOM and **state**; new key → create; missing key → remove.
  - Keys must be **unique among siblings** and **stable**. Best: the **id** from the data. Never `Math.random()`.
  - **Index keys** break when items are inserted, removed or reordered: **state sticks to the position**, not the item.
  - The key goes on the element **`map` returns**, and is **not** passed as a prop.
  - A **new key resets** a component's state: `<ChatBox key={contactId} />`.
</Callout>
