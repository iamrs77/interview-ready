## The idea

**`useEffect`** runs code **after** React has updated the screen. You use it to keep your component **in sync with something outside React**: a timer, a chat connection, a browser API, a server.

Think of a **hotel room**. When you check in, you switch on the air conditioning. When you check out, you switch it off. If you move to another room, you switch off the first one **before** switching on the next. An effect works the same way: a **setup** when the component appears, a **cleanup** when it goes away, and a cleanup then a new setup when something it depends on changes.

## What is a side effect?

Rendering must be **pure**: it only works out the JSX from props and state. A **side effect** is anything that touches the world **outside** that calculation:

- Starting a timer with `setInterval`
- Fetching data from a server
- Subscribing to events, like `window.addEventListener("resize", ...)`
- Connecting to a chat server or a WebSocket
- Changing the page title, or calling a non-React library

Side effects caused by a **user action**, like saving a form on click, go in the **event handler**. Side effects caused by the component **being on the screen** go in `useEffect`.

## The syntax

```jsx
useEffect(() => {
    // Setup: runs after render.

    return () => {
        // Cleanup: runs before the next setup, and when the component is removed.
    };
}, [dependencies]);
```

Two arguments:

1. A **setup function**. It can return a **cleanup function**.
2. A **dependency array**: the values the effect uses. React runs the effect again only when one of them has changed.

## When effects run

```jsx
function Page() {
    console.log("render");

    useEffect(() => {
        console.log("effect");
    });

    return <h1>Hello</h1>;
}
// render
// effect
```

React first calls the component, updates the DOM, and only **then** runs the effect. That's why an effect can safely read the DOM: it's already there. And because it usually runs after the browser has painted, a slow effect doesn't hold up the screen.

## The dependency array

The second argument decides **when** the effect runs again:

| You write | The effect runs |
| --- | --- |
| `useEffect(fn)` | After **every** render |
| `useEffect(fn, [])` | **Once**, after the first render |
| `useEffect(fn, [roomId])` | After the first render, and again whenever **`roomId` changed** |

React compares each dependency with its value from the last render, using `Object.is`. If **any** of them changed, the effect runs again.

The rule: **every value from the component that the effect uses** (props, state, and anything worked out from them) must be in the array. The ESLint rule **`react-hooks/exhaustive-deps`** checks this for you. Leaving one out to "run it less often" causes bugs with old values; see the stale closure section below.

## Cleanup

Here is a timer that counts seconds:

```jsx
import { useState, useEffect } from "react";

function Timer() {
    const [seconds, setSeconds] = useState(0);

    useEffect(() => {
        // Setup: start the timer.
        const intervalId = setInterval(() => {
            setSeconds((current) => current + 1);
        }, 1000);

        // Cleanup: stop the timer.
        return () => {
            clearInterval(intervalId);
        };
    }, []);

    return <p>Timer: {seconds}s</p>;
}
```

Without the cleanup, the timer keeps running after `Timer` is removed from the page. Show and hide it a few times, and several timers run at once.

The cleanup runs at **two** moments:

- **Before the effect runs again**, because a dependency changed.
- **When the component is removed** from the page (unmounted).

```jsx
function ChatRoom({ roomId }) {
    useEffect(() => {
        const connection = createConnection(roomId);
        connection.connect();

        return () => {
            connection.disconnect();
        };
    }, [roomId]);

    return <h1>Welcome to {roomId}</h1>;
}
```

When `roomId` changes from `"music"` to `"travel"`, the order is:

```text
connect music
disconnect music
connect travel
```

Cleanup is where you undo the setup: clear timers, remove event listeners, close connections, unsubscribe.

## Strict Mode runs effects twice in development

In development, with `<StrictMode>`, React runs every effect **setup, cleanup, setup** when the component first appears:

```text
connect music
disconnect music
connect music
```

This is on purpose. It's a test: if the app works the same after setup, cleanup, setup, your cleanup is correct. If you see two connections or two timers, the cleanup is **missing**. It happens only in development, never in production.

Don't "fix" it by blocking the second run with a ref. Fix the cleanup.

## Fetching data in an effect

```jsx
function UserProfile({ userId }) {
    const [user, setUser] = useState(null);

    useEffect(() => {
        let ignore = false;

        async function loadUser() {
            const response = await fetch("/api/users/" + userId);
            const data = await response.json();

            // Only use the answer if this effect is still the latest one.
            if (!ignore) {
                setUser(data);
            }
        }

        loadUser();

        return () => {
            ignore = true;
        };
    }, [userId]);

    if (!user) {
        return <p>Loading...</p>;
    }

    return <h1>{user.name}</h1>;
}
```

Two things to notice:

- **The effect function can't be `async`.** An async function returns a promise, and React expects the effect to return a cleanup function or nothing. Write an async function **inside** the effect and call it.
- **The `ignore` flag stops a race condition.** If `userId` changes from 1 to 2 quickly, the answer for user 1 may arrive **after** user 2's. The cleanup marks the old request as out of date, so its answer is ignored.

In real apps, data fetching usually goes through a library like TanStack Query, or a framework. See [Fetching Data](../data-and-state/fetching-data.mdx).

## The stale closure trap

This timer stops at **1**:

```jsx
function Timer() {
    const [seconds, setSeconds] = useState(0);

    useEffect(() => {
        const intervalId = setInterval(() => {
            // Wrong: seconds is always 0 in here.
            setSeconds(seconds + 1);
        }, 1000);

        return () => clearInterval(intervalId);
    }, []);

    return <p>{seconds}</p>;
}
```

The effect ran **once**, after the first render, so its function remembers that render's `seconds`, which is **0**. Every tick says `setSeconds(0 + 1)`. The screen shows 1 forever.

Two fixes:

- Use the **updater function**: `setSeconds((current) => current + 1)`. It doesn't need `seconds` at all. This is the best fix here.
- Add `seconds` to the dependency array. It works, but the interval is cleared and started again every second.

See [Puzzles: Stale Closures](../predict-and-debug/puzzles-stale-closures.mdx).

## Objects and functions as dependencies

```jsx
function SearchResults({ query }) {
    // A new object on every render.
    const options = { query: query, limit: 10 };

    useEffect(() => {
        fetchResults(options);
    }, [options]);
}
```

`options` is a **new object** on every render, and a new object is never `Object.is` equal to the old one. So the effect runs after **every** render. The same happens with functions made inside the component.

Fixes, best first:

1. **Make the object inside the effect**, and depend on the plain values: `[query]`.
2. Move it **outside the component** if it doesn't use props or state.
3. Keep it stable with `useMemo` or `useCallback`. See [useMemo and useCallback](./use-memo-and-use-callback.mdx).

## Lifecycle methods and effects

Class components had **lifecycle methods**. Interviewers often ask how they map to `useEffect`:

| Class component | With useEffect |
| --- | --- |
| `componentDidMount` | `useEffect(fn, [])` |
| `componentDidUpdate` | `useEffect(fn, [a, b])`, or no array to run after every render |
| `componentWillUnmount` | The **cleanup** function returned by the effect |

But the better way to think about effects is **"keep in sync"**, not "run at mount". An effect says: "while this component is on screen, keep it connected to room `roomId`". React works out when to start, stop and restart. See [Class Components and Lifecycle](../patterns/class-components.mdx).

## Do you need an effect at all?

Effects are for syncing with **outside** systems. Many effects in real code shouldn't be there:

- **A value worked out from props or state**, like a filtered list or a full name. Compute it while rendering. An effect plus state means an extra render and two things to keep in sync.
- **Something that happens because the user did something**, like sending a form. Put it in the event handler.

See [When Not to Use an Effect](./you-might-not-need-an-effect.mdx).

## Common mistakes

- **Missing cleanup.** Timers, listeners and connections pile up. Strict Mode's double run shows it.
- **Missing dependencies.** The effect uses old values. Trust the `exhaustive-deps` lint rule.
- **An `async` effect function.** `useEffect(async () => ...)` returns a promise, not a cleanup. Put the async function inside.
- **Setting state that the effect depends on.** `useEffect(() => setCount(count + 1), [count])` runs forever.
- **Objects or functions made during render as dependencies.** The effect runs after every render.
- **Using an effect for derived data.** `useEffect(() => setTotal(...), [items])` should be `const total = ...` while rendering.

## In the interview

**Likely question:** "What is `useEffect` for, and how does the dependency array work?"

> "`useEffect` runs code after React has updated the screen, to keep the component in sync with something outside React, like a timer, a subscription or a server. The dependency array says when to run it again: no array means after every render, an empty array means once after the first render, and `[a, b]` means again whenever `a` or `b` changed. The effect can return a cleanup function, which React runs before the next run and when the component is removed, so I can clear timers and close connections."

**Likely follow-up:** "Why does my effect run twice?"

**Answer:** "In development, Strict Mode runs every effect setup, cleanup, setup on purpose, to check that the cleanup is right. It doesn't happen in production. If the double run causes a bug, like two connections, the cleanup is missing."

**Another follow-up:** "Why can't the effect function be `async`?"

**Answer:** "React expects the effect to return either nothing or a cleanup function. An async function always returns a promise. So I define the async function inside the effect and call it, and I use a flag or an AbortController in the cleanup to ignore answers that arrive late."

<Callout title="Remember this" type="success">
  - **`useEffect(setup, deps)`** runs **after** React updates the screen. It's for syncing with things **outside** React.
  - No array → every render. **`[]`** → once after the first render. **`[a, b]`** → again when `a` or `b` changes.
  - **Cleanup** runs **before the next run** and **on unmount**. Use it to clear timers, remove listeners and disconnect.
  - **Strict Mode** runs setup, cleanup, setup in development, to catch missing cleanups.
  - Put **every** value the effect uses in the array (`exhaustive-deps`). Missing ones cause **stale closures**: use `setX(prev => ...)`.
  - The effect function **can't be async**. Ignore late answers with a flag in the cleanup.
  - Values you can compute and user actions **don't** need an effect.
</Callout>
