## The idea

With `useState`, you set the new value directly: `setCount(count + 1)`. With **`useReducer`**, you **describe what happened** instead: `dispatch({ type: "increment" })`. A separate function, the **reducer**, holds all the rules for how each kind of action changes the state.

Think of a **bank teller**. You don't open the ledger and change your balance yourself. You hand over a slip: "deposit 50". The teller follows the bank's rules and updates the ledger. The slip is the **action**, the teller is the **reducer**, and handing over the slip is **dispatch**.

## The syntax

```jsx
const [state, dispatch] = useReducer(reducer, initialState);
```

- **`reducer`**: a function `(state, action) => newState`.
- **`initialState`**: the starting state.
- **`state`**: the current state.
- **`dispatch`**: the function you call with an action.

An **action** is a plain object that describes what happened. By convention it has a **`type`**, and any extra data it needs.

## A counter with a reducer

```jsx
import { useReducer } from "react";

const initialState = { count: 0 };

function counterReducer(state, action) {
    switch (action.type) {
        case "increment":
            return { count: state.count + 1 };
        case "decrement":
            return { count: state.count - 1 };
        case "reset":
            return { count: 0 };
        default:
            throw new Error("Unknown action: " + action.type);
    }
}

function Counter() {
    const [state, dispatch] = useReducer(counterReducer, initialState);

    return (
        <div>
            <h1>Count: {state.count}</h1>
            <button onClick={() => dispatch({ type: "increment" })}>+</button>
            <button onClick={() => dispatch({ type: "decrement" })}>-</button>
            <button onClick={() => dispatch({ type: "reset" })}>Reset</button>
        </div>
    );
}
```

What happens on a click of **+**:

1. `dispatch({ type: "increment" })` queues the action and asks React for a re-render.
2. On the next render, React calls `counterReducer({ count: 0 }, { type: "increment" })`.
3. The reducer returns `{ count: 1 }`, and that becomes `state`.

Like the updater function in `useState`, actions are **queued**: dispatching `increment` twice in one click adds 2.

## The reducer must be pure

The reducer gets the current state and an action, and **returns** the next state. Nothing else:

- **Never change `state`.** Return a **new** object. `state.count++; return state;` returns the **same** object, so React sees no change and the screen doesn't update.
- **No side effects.** No fetching, no timers, no `localStorage`. Those go in event handlers or effects.
- **Same input, same output.** In development, Strict Mode calls the reducer **twice** to help you catch impure reducers.

Because it's a plain function, a reducer is easy to test without React:

```js noRun
const next = counterReducer({ count: 0 }, { type: "increment" });

console.log(next); // { count: 1 }
```

## Actions with data

Most actions carry data. Put it next to `type` in the action object:

```jsx
function todosReducer(todos, action) {
    switch (action.type) {
        case "added":
            return [...todos, { id: action.id, text: action.text, done: false }];
        case "toggled":
            return todos.map((todo) => {
                if (todo.id !== action.id) {
                    return todo;
                }

                return { ...todo, done: !todo.done };
            });
        case "deleted":
            return todos.filter((todo) => todo.id !== action.id);
        default:
            throw new Error("Unknown action: " + action.type);
    }
}

// In a component:
dispatch({ type: "added", id: crypto.randomUUID(), text: "Buy milk" });
dispatch({ type: "toggled", id: todoId });
```

Name actions after **what the user did** ("added", "toggled"), not how state should change ("setTodos"). Then the component reads like a list of events, and all the "how" lives in the reducer.

You'll also see a Redux style in a lot of code: an uppercase type, and the data in a field called **`payload`**, like `{ type: "SET_USERNAME", payload: "Ben" }`. Both styles work. Pick one per project and stick to it.

## A bigger example: manual and auto mode

The state can hold more than one value, and an effect can dispatch actions too. This counter counts by itself every second in "auto" mode:

```jsx
import { useReducer, useEffect } from "react";

const initialState = { count: 0, mode: "manual" };

function counterReducer(state, action) {
    switch (action.type) {
        case "increment":
            return { ...state, count: state.count + 1 };
        case "reset":
            return { ...state, count: 0 };
        case "toggleMode":
            return { ...state, mode: state.mode === "manual" ? "auto" : "manual" };
        default:
            throw new Error("Unknown action: " + action.type);
    }
}

function AutoCounter() {
    const [state, dispatch] = useReducer(counterReducer, initialState);

    useEffect(() => {
        if (state.mode !== "auto") {
            return;
        }

        const intervalId = setInterval(() => {
            dispatch({ type: "increment" });
        }, 1000);

        // Stops the timer when the mode changes back, or the component is removed.
        return () => clearInterval(intervalId);
    }, [state.mode]);

    return (
        <div>
            <h1>Count: {state.count}</h1>
            <p>Mode: {state.mode}</p>
            <button onClick={() => dispatch({ type: "increment" })}>+</button>
            <button onClick={() => dispatch({ type: "reset" })}>Reset</button>
            <button onClick={() => dispatch({ type: "toggleMode" })}>Toggle mode</button>
        </div>
    );
}
```

Each case copies the old state with `...state` and changes one field, so `mode` survives an `increment`. And the interval can call `dispatch` without a stale value, because `dispatch` only sends the action; the reducer always gets the **latest** state.

## useReducer vs useState

| | `useState` | `useReducer` |
| --- | --- | --- |
| Best for | One or two simple values | Several values that change together, or many kinds of updates |
| Update rules live | Spread across event handlers | In **one** reducer function |
| Testing the logic | Through the component | Call the reducer directly |
| Code size | Less | More: the reducer and the action types |

Start with `useState`. Switch to `useReducer` when one event updates several pieces of state, when the same update is copied into many handlers, or when the update logic is hard to follow. `useState` is actually built on top of the same mechanism inside React.

## useReducer with context

`useReducer` holds the state; [context](./use-context.mdx) delivers it. Together they give a small app-wide store, with no library. A common example is the logged-in user: many components show it, and a few change it.

**Step 1: create the context, the reducer and a provider.** They usually live together in one file, like `UserContext.jsx`:

```jsx
import { createContext, useContext, useReducer } from "react";

const UserContext = createContext(null);

const initialState = {
    username: "Ana",
};

function userReducer(state, action) {
    switch (action.type) {
        case "SET_USERNAME":
            return { ...state, username: action.payload };
        default:
            throw new Error("Unknown action: " + action.type);
    }
}

export function UserProvider({ children }) {
    const [state, dispatch] = useReducer(userReducer, initialState);

    return (
        <UserContext value={{ state, dispatch }}>
            {children}
        </UserContext>
    );
}

// Components call useUser() instead of useContext(UserContext).
export function useUser() {
    const value = useContext(UserContext);

    if (value === null) {
        throw new Error("useUser must be used inside <UserProvider>");
    }

    return value;
}
```

**Step 2: wrap the part of the app that needs the user.**

```jsx
function App() {
    return (
        <UserProvider>
            <Header />
            <Profile />
        </UserProvider>
    );
}
```

**Step 3: read the state and dispatch actions**, in any component inside the provider:

```jsx
function Header() {
    const { state } = useUser();

    return <header>Hi, {state.username}</header>;
}

function Profile() {
    const { state, dispatch } = useUser();

    function handleChange(event) {
        dispatch({ type: "SET_USERNAME", payload: event.target.value });
    }

    return (
        <div>
            <h2>Username: {state.username}</h2>
            <input
                value={state.username}
                onChange={handleChange}
                placeholder="Enter new username"
            />
        </div>
    );
}
```

Typing in `Profile` updates the `Header` too: both read the **same** state through the context. That's the difference from a [custom hook](./custom-hooks.mdx), where every component gets its own state.

And the entry file, with the React 18+ way to start an app:

```jsx
import { createRoot } from "react-dom/client";

const root = createRoot(document.getElementById("root"));
root.render(<App />);
```

Older code uses `ReactDOM.render(<App />, element)`. React 19 **removed** it.

One improvement for bigger apps: `dispatch` **never changes**, but `{ state, dispatch }` is a new object whenever the state changes. So a component that only **dispatches**, like a "Log out" button, still re-renders on every keystroke in the username box. Put them in **two** contexts:

```jsx
const UserStateContext = createContext(null);
const UserDispatchContext = createContext(null);

export function UserProvider({ children }) {
    const [state, dispatch] = useReducer(userReducer, initialState);

    return (
        <UserStateContext value={state}>
            <UserDispatchContext value={dispatch}>
                {children}
            </UserDispatchContext>
        </UserStateContext>
    );
}
```

Components that only read `UserDispatchContext` now never re-render when the state changes, because `dispatch` is always the same function.

This is the same idea as **Redux**: one store, actions describing what happened, and a pure reducer working out the next state. See [Redux](../data-and-state/redux.mdx).

## Common mistakes

- **Changing state inside the reducer.** `state.count++; return state;` doesn't update the screen. Return a new object.
- **Forgetting `...state`** when the state has several fields. Returning `{ count: 1 }` loses `mode`.
- **Side effects in the reducer**, like fetching or saving. Keep the reducer pure; do those in handlers or effects.
- **No `default` case.** A typo in an action type silently returns `undefined`, and the state is gone. Throw an error, or return `state`.
- **Reading state right after `dispatch`.** Like `useState`, the `state` in this render doesn't change. The new state arrives on the next render.

## In the interview

**Likely question:** "When would you use `useReducer` instead of `useState`?"

> "When the state has several values that change together, or there are many different ways to update it. Instead of setting values directly, components dispatch actions that say what happened, like `{ type: 'added', text }`, and one pure reducer function works out the next state. All the update rules live in one place, the components stay simple, and the reducer is easy to test because it's a plain function. For one or two simple values, `useState` is less code."

**Likely follow-up:** "How would you share reducer state across many components without Redux?"

**Answer:** "Call `useReducer` in a provider component, and pass `state` and `dispatch` down through context. Any component below can read the state and dispatch actions. Because `dispatch` never changes, I can put it in its own context so components that only dispatch don't re-render when the state changes."

<Callout title="Remember this" type="success">
  - **`const [state, dispatch] = useReducer(reducer, initialState)`**.
  - Components **dispatch actions** that say **what happened**: `dispatch({ type: "added", text })`.
  - The **reducer** `(state, action) => newState` holds all the update rules. It must be **pure**: no changing `state`, no side effects.
  - Return a **new object**. Copy the rest with **`...state`**. Throw or return `state` for unknown actions.
  - **useState** for simple values; **useReducer** for related values and many kinds of updates.
  - **useReducer + context** = a small store without a library. `dispatch` never changes, so it can get its own context.
</Callout>
