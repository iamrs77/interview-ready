## What is the coding round?

In a coding round, you solve **one or two small programming problems** while an interviewer watches. For example:

- "Given an array of numbers and a target, return the indexes of the two numbers that add up to the target."
- "Check if a string of brackets like `({[]})` is balanced."
- "Count the islands in a grid of land and water."

Think of a **driving test**. The examiner doesn't only check that you reach the end of the road. They watch you check the mirrors, signal and follow the rules. A coding round is the same: the interviewer watches **how** you reach the answer, not only the answer.

| | What to expect |
| --- | --- |
| Length | 45 to 60 minutes |
| Problems | 1 or 2. The second one is often harder, or a follow-up on the first ("what if the array is huge?"). |
| Where you code | A shared editor in the browser, like CoderPad or HackerRank. The interviewer sees every key you type. Some editors can run your code and some can't, so practice testing by hand. |
| Language | You pick. Here everything is in JavaScript. |
| Who | One engineer. They ask questions, give hints and take notes. |

A 45-minute round usually goes like this:

| Minutes | What happens |
| --- | --- |
| 0 to 5 | Hello, and a short intro about you |
| 5 to 10 | Read the problem, ask questions, write examples |
| 10 to 15 | Explain your idea: the simple way first, then a faster way |
| 15 to 35 | Write the code, talking as you go |
| 35 to 40 | Test it by hand and fix bugs |
| 40 to 45 | Time and space complexity, a follow-up, your questions |

The full method for those minutes, step by step, is on the next page: [How to Solve a Problem in an Interview](./interview-framework.mdx).

## What interviewers score

| They score | What good looks like |
| --- | --- |
| **Clear thinking** | You ask questions first, try small examples, and find a simple idea before a clever one. |
| **Correctness** | The code works for normal input **and** for edge cases: an empty array, one item, duplicates, negative numbers. |
| **Complexity** | You say the time and space **Big O** of your code, and why. See [Big O Notation](./foundations/big-o.mdx). |
| **Clean code** | Clear names, small steps, no copy-paste. Someone else could read it. |
| **Talking out loud** | The interviewer can follow your thinking. You listen to hints and use them. |
| **Testing** | You walk through an example by hand and find your own bugs before they do. |

Three things that surprise people:

- **A working simple answer beats an unfinished clever one.** If you can't find the fast way, code the slow way and say so.
- **Hints are normal.** Taking a hint costs a little. Ignoring one costs a lot.
- **Silence hurts.** The interviewer can't give credit for thinking they can't hear.

## How this track is ordered

This track is ordered **by pattern**. A pattern is one way of solving that fits many problems, like "two pointers" or "sliding window".

Why patterns? There are thousands of interview problems, but only about 15 to 20 patterns behind them. Most problems are one pattern in disguise. Learn the pattern, and you can solve problems you have never seen.

Think of cooking. If you memorize 500 recipes, you are lost when one ingredient is missing. If you learn a few methods, like frying, boiling and baking, you can cook almost anything.

## How much practice is enough

Quality beats count. 150 problems you really understand beat 500 you rushed through.

A plan that works:

1. **Learn one pattern.** Read its page here, then solve its classic problems yourself, without looking at the code.
2. **Practice that pattern.** Solve the matching NeetCode group (see below).
3. **Stuck for 25 minutes?** Read the answer and understand it. Then close it, and write it again yourself from scratch.
4. **Solve it again later.** After about 3 days, and again after a week or two. If you can't, it isn't learned yet.
5. **Mix it up.** In a real interview, nobody tells you the pattern. Once you have done a few sections, practice problems in random order.
6. **Practice like the real thing.** Set a 30 to 45 minute timer, talk out loud, and test by hand before you press Run.

Most interview problems are around LeetCode **Medium**. Spend most of your time there. Do a few Easy ones to learn each pattern, and a few Hard ones at the end.

You are ready when:

- you can name the pattern of a new Medium problem within about 5 minutes;
- you can solve most Mediums in 25 to 30 minutes while talking out loud;
- you can write the common templates (binary search, BFS, sliding window, backtracking) from memory, without bugs;
- you can say the Big O of your code without guessing.

## Run every code block

Every code block in this track runs as written. Try them in the **JS Playground**:

1. Open it with the **JS Playground** button in the sidebar, under search. Or press `Ctrl` + `` ` `` (the backtick key, usually under Esc).
2. Paste a code block and press `Ctrl` + `Enter` to run it. The output shows below the code.
3. Press `Esc` to close it. Your code is kept in this browser for next time.

When some code confuses you, change the input, or add a `console.log` inside the loop and watch each step. That is the fastest way to understand it.

On a phone, use the round **JS** button in the bottom-right corner.
