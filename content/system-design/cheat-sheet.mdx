## The interview in 6 steps

Full lesson: [The Interview Framework](./interview-framework.mdx).

| Step | Time | What you do |
| --- | --- | --- |
| **1. Requirements** | 5 min | Top 3 features. Say what is out of scope. Qualities with numbers: scale, speed, uptime, consistency |
| **2. Core entities** | 2 min | List the main "things": User, Order, Ticket... |
| **3. API** | 5 min | One endpoint per feature. User ID comes from the token |
| **4. Data flow** | 5 min | Only for pipelines (crawler, analytics). Skip otherwise |
| **5. High-level design** | 10–15 min | Simplest boxes and arrows that work, one feature at a time |
| **6. Deep dives** | 10 min | Check each quality. Fix the weak spots. Say the tradeoffs |

**Always:** think out loud, start simple, keep servers stateless, and say "I chose X because..., the downside is...".

## Numbers to know

Full lesson: [Capacity Estimation](./hld-basics/capacity-estimation.mdx).

**Quick math**

- One day ≈ **100,000 seconds**. So **requests per second ≈ requests per day ÷ 100,000**.
- **Peak ≈ 2 to 3 times** the average.
- **Storage per year** = items per day × size of one item × 365.
- 1 million × 1 KB = **1 GB**. 1 billion × 1 KB = **1 TB**.

**Speed**

| Action | Time |
| --- | --- |
| Read from memory (RAM) | 100 ns |
| Random read from an SSD | 0.1 ms |
| Round trip inside one data center | 0.5 ms |
| Read from Redis | under 1 ms |
| Database query using an index | 1–10 ms |
| USA (East Coast) ↔ Europe | about 80 ms |
| India ↔ USA | about 200 ms |

**What one machine can handle (roughly)**

| Machine | Per second |
| --- | --- |
| App server | 1,000–10,000 requests |
| SQL database | a few thousand to about 10,000 simple queries |
| Redis | about 100,000 operations |
| Kafka broker | hundreds of thousands of messages |
| WebSocket server | hundreds of thousands of open connections (total, not per second) |

**Sizes**

| Thing | Size |
| --- | --- |
| A short post or chat message | a few hundred bytes |
| A user profile row | about 1 KB |
| A photo | 200 KB to 2 MB |
| 1 minute of HD video | 50–100 MB |

**Uptime**

| Availability | Down per year | Down per month |
| --- | --- | --- |
| 99.9% (three nines) | about 8.8 hours | about 44 minutes |
| 99.99% (four nines) | about 53 minutes | about 4.4 minutes |
| 99.999% (five nines) | about 5 minutes | about 26 seconds |

## Which tool for which problem

| You need to... | Use |
| --- | --- |
| Spread traffic across servers | [Load balancer](./hld-basics/load-balancing.mdx) |
| Serve the same data to many readers | [Cache (Redis)](./caching/what-is-caching.mdx) + [read replicas](./databases/replication.mdx) |
| Store images, videos, files | [Object storage (S3)](./advanced-components/storage-types.mdx) + [CDN](./caching/cdn.mdx) |
| Keep money, orders, relations correct | [SQL database (PostgreSQL)](./databases/sql-vs-nosql.mdx) with [transactions](./databases/transactions-acid.mdx) |
| Write a huge amount of simple data | NoSQL like Cassandra or DynamoDB ([SQL vs NoSQL](./databases/sql-vs-nosql.mdx)) |
| Grow past one database | [Sharding](./databases/partitioning-sharding.mdx) with [consistent hashing](./databases/consistent-hashing.mdx) |
| Search text | [Elasticsearch (inverted index)](./advanced-components/search.mdx) |
| Find things near a location | [Geospatial index (geohash)](./advanced-components/geospatial-indexing.mdx) |
| Do work later, absorb spikes | [Queue](./messaging/message-queues-pub-sub.mdx) + [background workers](./advanced-components/background-jobs.mdx) |
| Stream events many services can read and replay | [Kafka](./messaging/kafka.mdx) |
| Count in real time (views, clicks) | [Stream processing](./advanced-components/batch-vs-stream.mdx) with time windows |
| Count unique users or top items cheaply | [HyperLogLog, Count-Min Sketch](./advanced-components/probabilistic-data-structures.mdx) |
| Push updates to users instantly | [WebSockets or SSE](./foundations/polling-websockets-sse.mdx) |
| Counters, leaderboards, rate limits, locks | [Redis](./caching/redis.mdx) |
| Unique IDs across many servers | [Snowflake IDs](./distributed-systems/distributed-id-generation.mdx) |
| Never sell the same seat twice | [Locks](./databases/locking.mdx) or a reservation that expires |
| Never charge twice | [Idempotency keys](./messaging/idempotency.mdx) |
| Many steps across services | [Saga](./distributed-systems/saga-pattern.mdx) |
| Save data and send an event safely | [Outbox](./distributed-systems/outbox-pattern.mdx) or [CDC](./distributed-systems/change-data-capture.mdx) |
| Upload big files | [Presigned URLs + chunked upload](./advanced-components/file-upload-download.mdx) |
| Feeds with celebrities | [Fan-out: push for most, pull for celebrities](./advanced-components/hot-keys-fan-out.mdx) |
| Protect against overload | [Rate limiting](./reliability-security/rate-limiting.mdx), [backpressure](./reliability-security/backpressure.mdx), [circuit breaker](./reliability-security/circuit-breaker.mdx) |
| Survive a server or region dying | [Redundancy and failover](./reliability-security/redundancy-failover.mdx) |

## Tradeoffs, one line each

| Choice | You gain | You give up |
| --- | --- | --- |
| **Vertical vs horizontal scaling** | Simple (bigger machine) | No limit, survives failures (more machines) |
| **SQL vs NoSQL** | Relations and transactions | Easy scaling and flexible data |
| **Consistency vs availability** ([CAP](./distributed-systems/cap-theorem.mdx)) | Always correct data | Always answering when the network breaks |
| **Strong vs eventual consistency** | Everyone sees the newest data | Speed and uptime |
| **Cache** | Fast reads | Data can be a little old |
| **Normalize vs denormalize** | No duplicate data | Fast reads without joins |
| **Fan-out on write vs on read** | Fast feed reads | Cheap posting for celebrities |
| **Sync vs async calls** | Instant answer, simple | Survives slow or broken services |
| **Polling vs WebSockets** | Simple, stateless | Real-time, but open connections to manage |
| **Pessimistic vs optimistic locking** | Safe when many fight for the same row | Fast when conflicts are rare |
| **Sessions vs JWT** | Easy logout | No lookup on every request |
| **Batch vs stream** | Simple and cheap | Fresh results |
| **Exact vs approximate counting** | Exact numbers | Tiny memory |
| **Monolith vs microservices** | Simple to build and run | Teams and parts scale on their own |
| **Sync vs async replication** | No data loss | Faster writes |

## Before you walk in

<Callout title="Remember this" type="success">
  - **Requirements first.** Never draw before you agree on what to build.
  - **Say the numbers:** users, requests per second, read-to-write ratio, storage.
  - **Simple first**, then make it strong in the deep dives.
  - **Every box needs a reason.** Don't add Kafka or sharding "just because".
  - **Say what fails:** "If this server dies...", "If this region goes down...".
  - **Always say the tradeoff** of each choice.
  - **Think out loud** the whole time.
</Callout>
