## Guide

**[The Interview Framework](./interview-framework.mdx)**

- **6 steps:** Requirements → Core Entities → API → (Data Flow) → High-Level Design → Deep Dives.
- **Requirements first:** top 3 features, plus clear qualities with numbers.
- **Do math only if it changes a decision.**
- **One API endpoint per feature.**
- **Simple design first**, then make it strong in the deep dives.
- **Always say the tradeoff:** "I chose X because..., the downside is...".

## 1. Foundations

**[Client-Server Architecture](./foundations/client-server.mdx)**

- The **client** asks. The **server** does the work and answers.
- A client can be a browser, a mobile app, or even another server.
- **Never trust the client.** Do important checks on the server.
- One server can serve many clients. Big apps use many servers.
- Every design starts with **Client → Server → Database**.

**[How the Internet Works](./foundations/how-the-internet-works.mdx)**

- The internet is **many networks joined together**.
- Data is cut into **packets**. **Routers** pass them along, hop by hop.
- Packets can arrive **out of order** or get **lost**. TCP fixes this.
- **Latency** = time for one trip. **Bandwidth** = how much data at once.
- **Distance adds delay.** India ↔ USA is about 200 ms per round trip. Keep servers close to users.

**[IP Addresses and Ports](./foundations/ip-addresses-and-ports.mdx)**

- **IP address = which computer.** **Port = which app** on that computer.
- **IPv4** (`192.168.1.10`) is running out. **IPv6** (`2001:db8::1`) is the long new format.
- **Public IP** = reachable from the internet. **Private IP** = only inside one network.
- **NAT** lets many private devices share one public IP.
- Keep app servers and databases on **private IPs**. Only the load balancer is public.
- Ports to know: **80** HTTP, **443** HTTPS, **5432** PostgreSQL, **6379** Redis.

**[DNS](./foundations/dns.mdx)**

- DNS turns **names into IP addresses**. It is the internet's contact list.
- Lookup order: **browser cache → computer cache → resolver → root → .com → the domain's name server**.
- Answers are **cached for the TTL**, so DNS changes are not instant.
- **A** = IPv4, **AAAA** = IPv6, **CNAME** = an alias to another name.
- **GeoDNS** sends users to the nearest region. A **load balancer** does the rest.

**[TCP vs UDP](./foundations/tcp-vs-udp.mdx)**

- **TCP = safe:** handshake first, every packet arrives, in order. A little slower.
- **UDP = fast:** no handshake, no resending, no order.
- The TCP handshake costs **one round trip**, so reuse open connections.
- **TCP by default.** UDP for **voice and video calls and games**, where late data is useless.
- **Streaming video** (even live) is not UDP: it is HTTP chunks through a CDN.
- **HTTP/3** runs on **QUIC**, which is built on UDP.

**[HTTP and HTTPS](./foundations/http-and-https.mdx)**

- **HTTP** = request (method, path, headers, body) and response (status code, headers, body).
- **HTTP is stateless.** Send a cookie or token with every request.
- **HTTPS = HTTP + TLS:** private, can't be changed, and you know it's the right server.
- A **certificate** is the server's ID card, signed by a trusted company.
- A new HTTPS connection costs about **2 round trips**. Reuse connections.
- **TLS usually ends at the load balancer.**
- **HTTP/2:** many requests on one connection. **HTTP/3:** runs on QUIC (UDP).

**[HTTP Methods, Status Codes and Headers](./foundations/http-methods-status-codes-headers.mdx)**

- **Methods:** `GET` read, `POST` create, `PUT` replace, `PATCH` change a part, `DELETE` remove.
- `GET` is **safe**. `GET`, `PUT` and `DELETE` are **idempotent**. `POST` is **not**, so use an **idempotency key**.
- **2xx** success, **3xx** go elsewhere, **4xx** client mistake, **5xx** server problem.
- **401** not logged in, **403** not allowed, **409** conflict, **429** slow down.
- Retry **5xx** and **429** only if the request is safe to repeat (idempotent, or has an idempotency key), with **backoff and jitter**. Don't retry other **4xx**.
- Headers to know: `Content-Type`, `Authorization`, `Cache-Control`, `ETag`, `Location`, `Retry-After`.

**[REST APIs](./foundations/rest-apis.mdx)**

- REST: **resources** (nouns) with **URLs**, and **HTTP methods** as the actions.
- Plural nouns, nest only for "belongs to", filters in the **query string**.
- **Path param** = which one (`/orders/42`). **Query param** = filter, sort, search, page (`/orders?page=2&limit=20`).
- **`QUERY`** = the safety of `GET` + the body of `POST`. Use it for searches too big or complex for a URL (or `POST /search` until it's supported).
- Use the **right status code**, plus a clear error body.
- **One endpoint per feature.**
- Take the **user from the token**, never from the body.
- **Page** big lists. **Version** the API when it changes.

**[gRPC and GraphQL](./foundations/grpc-and-graphql.mdx)**

- **RPC** = call a function that runs on another server.
- **gRPC:** fast, binary (Protocol Buffers), typed contracts, HTTP/2. Best **between services**.
- **GraphQL:** one query asks for **exactly the fields** you need. No over-fetching, fewer round trips.
- GraphQL downsides: **harder caching**, expensive queries, the N+1 problem.
- **REST by default**, gRPC inside, GraphQL for many different screens.

**[Polling, WebSockets and SSE](./foundations/polling-websockets-sse.mdx)**

- **Polling:** ask every few seconds. Simple, but wasteful and delayed.
- **Long polling:** the server holds the request until there is news.
- **SSE:** one open connection, **server → client** only. Great for notifications and live updates.
- **WebSockets:** one open connection, **both ways**. Great for chat and games.
- Open connections are hard to scale: use **pub/sub** to reach users on other servers.
- Pick the **simplest** option that is fast enough.

**[Cookies, Sessions and JWT](./foundations/cookies-sessions-jwt.mdx)**

- **Cookies:** small data the browser keeps and sends back **automatically**.
- **Session:** the server stores your details. The cookie holds only an **ID**. Easy to log out.
- **JWT:** a **signed** token holding your details. No lookup, but **hard to cancel**.
- JWTs are signed, **not encrypted**. Never put secrets inside.
- Sign with a **private key** (`RS256`), check with the **public key**, and check `exp`. In browsers, keep tokens in `HttpOnly` cookies.
- Use **short access tokens + refresh tokens**.
- Cookie flags: `HttpOnly`, `Secure`, `SameSite`.

**[Reverse and Forward Proxies](./foundations/proxies.mdx)**

- A **proxy** sits in the middle and passes messages on.
- **Forward proxy** = works for **clients**. Hides who they are, filters and caches their traffic.
- **Reverse proxy** = works for **servers**. Load balancing, HTTPS, caching, routing, security.
- Load balancers and API gateways are **special kinds of reverse proxy**.
- Examples: **Nginx, HAProxy, Envoy, Cloudflare**.

**[What Happens When You Type a URL](./foundations/what-happens-when-you-type-a-url.mdx)**

- The journey: **URL and cache → DNS → TCP → TLS → HTTP request → CDN / load balancer → app server → cache / database → response → page**.
- A new HTTPS connection costs **2 round trips** (TCP + TLS 1.3). The request itself is **1 more**.
- India ↔ USA: about **600 ms plus server time** before the first byte, on a new connection.
- **Travel is most of the wait.** Cut round trips: a **CDN edge** nearby, **reused connections**, **HTTP/3**.
- The HTML is only the start: **CSS, JS, images and API calls** follow, many at once on one HTTP/2 connection.
- In the interview: **every step briefly, in order**, then go deep where asked.

## 2. High-Level Design Basics

**[Scalability](./hld-basics/scalability.mdx)**

- **Scalable** = handle more load by adding resources, without a redesign.
- **Vertical** = a bigger machine. Simple, but it has a ceiling and is a single point of failure.
- **Horizontal** = more machines. Almost no ceiling and survives failures, but more complex.
- Horizontal scaling needs **stateless** servers.
- Usual order: **separate DB → more app servers → cache and replicas → shard → CDN and regions**.
- The **database** is almost always the hard part.

**[Availability and Reliability](./hld-basics/availability-reliability.mdx)**

- **Availability** = is it up? **Reliability** = does it work correctly over time?
- Each extra **nine** = 10× less downtime. **99.9% ≈ 9 hours a year. 99.99% ≈ 53 minutes a year.**
- Parts **in a chain** multiply availability down. Parts **side by side** multiply it up.
- A **single point of failure** takes everything down. Ask "what if this one dies?"
- Fix with **redundancy, failover, health checks, many zones** and careful deploys.

**[Latency, Throughput and QPS](./hld-basics/latency-throughput-qps.mdx)**

- **Latency** = the time for one request. **Throughput** = how many requests finish per second.
- **QPS / RPS** = requests per second. Design for the **peak**, not the average.
- The average hides slow requests. Use **p50 and p99**.
- With **fan-out**, rare slowness on each server becomes common slowness for users.
- **Busy servers get slow.** Add capacity before you hit 100%.
- **Batching**: more throughput, more latency. **Caching**: better at both.

**[Queueing Basics](./hld-basics/queueing-basics.mdx)**

- **Utilization** = arrival rate ÷ service rate = how busy the server is.
- Waiting **explodes** near 100%. In the simple M/M/1 model, wait = utilization ÷ (1 − utilization) × service time: 50% → 1×, 90% → 9×, 99% → 99×.
- **Little's Law:** items in the system = arrival rate × time in the system. 1,000 per second × 0.2 s = 200 in flight.
- A **slow dependency** means more requests in flight, so threads and connection pools run out.
- Leave **headroom** on latency-sensitive servers. Batch jobs can run near 100%.
- **Bound every queue**, use timeouts, and shed load or push back when full.
- Queues create **tail latency**: unlucky requests wait behind a burst.

**[Stateless vs Stateful Servers](./hld-basics/stateless-vs-stateful.mdx)**

- **State** = what a server remembers between requests.
- **Stateless** servers: any server can answer any request. Easy to add, remove and replace.
- Move state to **Redis** (sessions), the **database** (permanent data), **S3** (files), or a **token** the client carries.
- Some parts must be stateful: **databases, caches, live connections, game servers**.
- **Sticky sessions** keep a user on one server. A quick fix, but uneven load and lost sessions on a crash.

**[Load Balancing](./hld-basics/load-balancing.mdx)**

- A **load balancer** spreads requests across servers and skips dead ones. Users see one address.
- **Round robin** = in turn. **Least connections** = least busy. **Hashing** = same key, same server.
- `hash % N` moves most keys when servers change. **Consistent hashing** moves only a few.
- **L4** = fast, sees only IP and port. **L7** = reads HTTP, routes by URL, header or cookie.
- **Drain** a server before removing it, so requests in progress can finish.
- Never just one load balancer: use **active-passive** with a floating IP, **active-active**, or a managed cloud LB.

**[Health Checks and Service Discovery](./hld-basics/health-checks-service-discovery.mdx)**

- A **health check** is a regular "are you okay?" test, usually `GET /health`.
- Fail a few times **in a row** → removed. Pass a few times → added back.
- **Liveness** = is it running? (restart if not). **Readiness** = can it take traffic? (remove if not).
- Readiness checks only what the server **owns**. If it checks a shared database, one slow database can fail every server at once.
- **Service discovery** = find a service's current addresses by name, using a **registry**.
- **Client-side** (Eureka) vs **server-side** (load balancer, Kubernetes Service).

**[API Gateway](./hld-basics/api-gateway.mdx)**

- An **API gateway** is one front door for many services.
- Its jobs: **routing, login checks, rate limits, TLS**, logging, and sometimes combining answers.
- Check **who you are** once at the gateway. Services still check **what you may do** with their data.
- **Load balancer** = spread traffic over copies of one service. **Gateway** = route to different services and apply API rules.
- Run several gateway copies, and keep business logic out of it.

**[Monolith vs Microservices](./hld-basics/monolith-vs-microservices.mdx)**

- **Monolith** = one app, one deploy. Simple and fast to build, but hard to change as it grows.
- **Microservices** = many small services, each with its own data and deploy. Teams move freely, but the network makes everything harder.
- **Three-tier** = split by layer. **SOA** = a few large shared services and a central bus.
- Start with a **modular monolith**. Split when **teams or load** really need it.
- Move piece by piece with the **strangler pattern**, never with a big rewrite.

**[Capacity Estimation](./hld-basics/capacity-estimation.mdx)**

- The goal is the **order of magnitude**, not the exact number.
- **1 day ≈ 100,000 seconds.** 1 million a day ≈ 10 per second (about 12 exactly).
- **Peak ≈ 2 to 3 × average.**
- **A million × 1 KB = 1 GB. A billion × 1 KB = 1 TB.**
- Memory **100 ns**, SSD **0.1 ms**, same data center **0.5 ms**, across an ocean **80 to 200 ms**.
- Every number should lead to a **decision**: cache, shard, S3, CDN.

**[Scaling Reads](./hld-basics/scaling-reads.mdx)**

- Most systems are **read-heavy**.
- Fix in order: **index → cache → read replicas → CDN → precompute**.
- Replicas can be a little **behind**. Read your own new writes from the primary.
- Say the read-to-write ratio early. It tells you this pattern is needed.

**[Scaling Writes](./hld-basics/scaling-writes.mdx)**

- Replicas and caches don't help writes: **every copy must store every write**. With one primary, all writes go through it.
- First make writes cheaper: fewer indexes, and **batch** many rows into one write.
- A **queue** absorbs spikes. Workers write at a steady pace.
- **Sharding** splits writes across many primaries. Pick a key that spreads writes evenly.
- **Write-friendly databases** (Cassandra, LSM trees) handle huge write volumes.
- **Counters:** Redis plus a regular save, batching, or sharded counters. Never one hot row.

## 3. Databases

**[SQL vs NoSQL](./databases/sql-vs-nosql.mdx)**

- **SQL:** tables, fixed schema, joins, strong transactions. Ask any question.
- **NoSQL types:** key-value, document, wide-column, graph. Each is great at one kind of access.
- NoSQL usually means **no joins**, so you design around your queries and copy data.
- **Default to PostgreSQL.** Switch only with a clear reason.
- Pick by **access pattern**, and say the reason out loud.
- Big systems often use **several databases** for different jobs.

**[Schemas, Relationships and Keys](./databases/schemas-and-keys.mdx)**

- A **schema** is the fixed shape of your tables: columns, types and rules.
- **Primary key:** unique, never empty, never changes. Use `BIGINT` or a UUID, not an email.
- **Foreign key:** points to another table's primary key. The database protects the link.
- **One-to-many:** foreign key on the "many" side. **Many-to-many:** a join table.
- Store **money as whole cents**, never as a float.
- Foreign keys don't work **across shards or services**. The app must check there.

**[Normalization vs Denormalization](./databases/normalization.mdx)**

- **Normalization:** each fact stored once. No update, insert or delete bugs.
- **Denormalization:** copy data where it is read, for faster reads.
- Every copy must be **kept in sync**: same transaction, events, or batch jobs.
- The original is the **source of truth**. Copies can always be rebuilt.
- **Start normalized**, then denormalize the specific reads that are too slow.
- A price saved on an order is a **snapshot**, not a copy to sync.

**[Indexes: B-Trees and LSM Trees](./databases/indexes.mdx)**

- An **index** is a sorted copy of a column with pointers to rows. No index means a **full scan**.
- **B-tree:** short, wide, sorted tree. Fast reads and ranges. The default in SQL databases.
- **LSM tree:** memtable, then sorted files, then compaction. Very fast writes.
- **Multi-column index:** works from the leftmost column. Exact matches first, range or sort last.
- Every index **slows writes** and uses space. Index your main queries only.

**[Transactions and ACID](./databases/transactions-acid.mdx)**

- A **transaction** makes several steps **all or nothing**.
- **ACID:** Atomicity (all or nothing), Consistency (rules hold), Isolation (as if run one at a time), Durability (committed means saved).
- `COMMIT` makes it final. `ROLLBACK` undoes it. Crashes roll back on their own. After a failed statement, **your app** sends `ROLLBACK`.
- Durability comes from the **write-ahead log** on disk.
- Keep transactions **short**. No slow outside calls inside them.
- Across services, use a **saga** or **2PC**, not a database transaction.

**[Isolation Levels](./databases/isolation-levels.mdx)**

- **Isolation** = how much transactions running at the same time see of each other.
- Problems: **dirty read**, **non-repeatable read**, **phantom read**, **lost update**, **write skew**.
- Levels: read uncommitted, **read committed**, **repeatable read**, **serializable**. Stronger is safer but slower.
- **Defaults:** PostgreSQL = read committed. MySQL = repeatable read.
- **Same name, different rules:** at repeatable read, PostgreSQL stops lost updates (with an error to retry). MySQL doesn't.
- **MVCC** keeps old row versions, so readers and writers don't block each other.
- Keep the default, and protect hot spots with **atomic updates, row locks or serializable** plus retries.

**[Locks and Deadlocks](./databases/locking.mdx)**

- **Row locks** are normal. **Table locks** (some `ALTER TABLE`) can block a whole table.
- **Deadlock:** two transactions wait for each other. The database kills one. **Lock in the same order** and retry.
- **Pessimistic:** `SELECT ... FOR UPDATE`, lock first. For hot, short, high-clash spots.
- **Optimistic:** a `version` column, check on save. For rare clashes and long user edits.
- A **conditional update** (`... WHERE stock >= 1`) often replaces a lock.
- `SKIP LOCKED` lets many workers take different jobs from one table.

**[Replication](./databases/replication.mdx)**

- **Primary** takes writes, **replicas** copy its change log and serve reads.
- **Sync:** no data loss, slower writes. **Async:** fast, but replicas lag and the last writes can be lost.
- **Replica lag** breaks "I just saved it, where is it?" Read your own writes from the primary.
- **Multi-leader** gives write conflicts. **Leaderless** uses quorums: W + R greater than N.
- **Failover:** notice, choose, promote, redirect. Watch out for **split brain**.
- **Replication is not a backup.** Deletes are copied too.

**[Partitioning and Sharding](./databases/partitioning-sharding.mdx)**

- **Partitioning:** split a table on **one** machine. **Sharding:** split data across **many** machines.
- Shard only when **writes or data size** outgrow one machine. Try indexes, caching, replicas first.
- A good **shard key**: even spread, matches the main query, keeps related data together.
- **Range** sharding is good for ranges but makes hot spots. **Hash** sharding spreads evenly.
- Watch for **hot shards** and slow **scatter-gather** queries across all shards.
- Start with **many logical shards** so you can move them later.

**[Consistent Hashing](./databases/consistent-hashing.mdx)**

- **Hash mod N** moves almost every key when N changes. Bad for caches and databases.
- **The ring:** hash servers and keys onto a circle. A key belongs to the **next server clockwise**.
- **Add a server:** it takes keys from one neighbor only. **Remove one:** its keys go to the next server.
- Only about **1/N** of the keys move.
- **Virtual nodes:** many spots per server give an even spread and share the load when a server dies.
- Used by **Cassandra**, **Dynamo**, and cache clients. **Redis Cluster** uses 16,384 slots instead.

**[Connection Pooling](./databases/connection-pooling.mdx)**

- Opening a connection is **slow**: TCP, TLS, login, and a new process in PostgreSQL.
- A **pool** keeps connections open. Requests **borrow and return** them.
- **Always return** connections, or the pool leaks and the app freezes.
- **Small pools** usually beat big ones. Remember: servers × pool size = total connections.
- **PgBouncer** in **transaction mode** lets many app servers share a few real connections.

**[PostgreSQL vs MySQL](./databases/postgresql-vs-mysql.mdx)**

- **Both are good.** Pick one, give a reason, and move on.
- **Defaults differ:** PostgreSQL = read committed, MySQL = repeatable read. A failed statement aborts the whole transaction in PostgreSQL, but only that statement in MySQL.
- **MySQL (InnoDB)** stores rows **inside the primary key index**. Keep primary keys short and growing. Random UUIDs hurt inserts.
- **PostgreSQL** stores rows in a **heap**. Old versions stay in the table until **VACUUM**. MySQL keeps them in the **undo log**.
- PostgreSQL can **roll back schema changes**. MySQL commits them at once.
- PostgreSQL extras: `JSONB` with GIN, arrays, extensions, `RETURNING`. Its connections are processes, so use **PgBouncer**.

**[Cassandra and DynamoDB](./databases/cassandra-dynamodb.mdx)**

- Primary key = **partition key** (which machines) + **sort key** (order inside the partition).
- Every query needs the **partition key**. Design **one table per query**, and copy data. No joins.
- Cassandra writes are fast: **LSM tree**, no read before write. Deletes leave **tombstones**.
- **Tunable consistency:** 3 copies, `QUORUM` reads and writes (2 + 2 > 3). DynamoDB: eventual reads by default, strong if you ask.
- Watch for **hot partitions**: pick a key that spreads traffic, add a **time bucket** to stop endless growth.
- Secondary indexes are weak in Cassandra. DynamoDB has **GSIs**, which are eventually consistent.
- **Default to PostgreSQL.** Pick these for huge writes, endless data and reads by a known key.

**[How a Query Runs](./databases/how-a-query-runs.mdx)**

- SQL says **what**. The **planner** decides **how**.
- Steps: **parse, rewrite, plan, execute**.
- `EXPLAIN ANALYZE` shows the plan and the real time.
- **Seq Scan** reads everything. **Index Scan** jumps to matches. A full scan is fine for big result sets.
- Common causes of slowness: missing index, unusable index, old statistics, N+1 queries.

**[SQL Fundamentals](./databases/sql-fundamentals.mdx)**

- `SELECT` columns `FROM` a table `WHERE` rows match, `ORDER BY`, `LIMIT`.
- `JOIN` combines tables on matching IDs. `LEFT JOIN` keeps rows with no match.
- `GROUP BY` with `COUNT`, `SUM`, `AVG`. `WHERE` filters rows, `HAVING` filters groups.
- Use `IS NULL`, never `= NULL`.
- `UPDATE` or `DELETE` without `WHERE` hits **every row**.

## 4. Caching and CDN

**[What is Caching](./caching/what-is-caching.mdx)**

- A cache keeps a **copy** of popular data in a **fast place**, usually memory.
- **Hit** = found in the cache, fast. **Miss** = go to the database, then save a copy.
- **Hit ratio** = hits / all lookups. 90%+ is common for popular data.
- Memory is about **1,000 times faster** than an SSD. Redis reads take **under 1 ms**.
- Caches live in the **browser, CDN, app server and a shared cache** like Redis.
- Cache data that is **read often, changed rarely, and slow to get**.

**[Caching Strategies](./caching/caching-strategies.mdx)**

- **Cache-aside:** the app checks the cache, loads from the database on a miss. **The default.**
- **Read-through:** the cache loads from the database itself.
- **Write-through:** write to the cache and the database together. Always fresh, slower writes.
- **Write-behind:** write to the cache now, the database later. Fast, but **can lose data**.
- On a write, **update the database, then delete the key**. Don't update the cached value.

**[Cache Invalidation and TTL](./caching/cache-invalidation-ttl.mdx)**

- **Stale data** = the cache still has the old copy after the database changed.
- **Delete on write:** update the database **first**, then **delete** the key.
- **Delete, don't update** the cached value. Deletes can't arrive "in the wrong order".
- **TTL** = an expiry timer. A safety net for anything you missed.
- Pick the TTL by asking **how bad old data is**. Add **jitter** so keys don't expire together.
- Decisions that must be exact, like **holding a seat** or **paying from a balance**, always **check the database**. A cache with a very short TTL only helps **show** that data.

**[Cache Eviction: LRU, LFU, FIFO](./caching/cache-eviction.mdx)**

- **Eviction** = removing items because the cache is **full**. Expiry = because the **TTL** ran out.
- **LRU:** remove the item used **longest ago**. The default choice.
- **LFU:** remove the item used **least often**. Good for stable favorites.
- **FIFO:** remove the item **added first**. Simple, but ignores popularity.
- LRU in JS: a `Map`. On read, delete and re-add the key. When full, remove the **first** key.
- Redis defaults to `noeviction`. For a cache, set `allkeys-lru`.

**[Redis](./caching/redis.mdx)**

- Redis = **in-memory key-value store**. Reads and writes in under 1 ms.
- Main uses: **cache, counter, rate limiter, leaderboard, lock, pub/sub**.
- Commands are **atomic**, so counters are safe. Locks can **expire or be lost** in a failover: use them to save work, and let the database check correctness.
- Memory is limited. Keep only **hot** data in it.
- Usually **not** the main database.
- **Fast with one thread:** data in **RAM**, no **locks** between threads, and an **event loop** that serves many connections. The catch: one slow command (like `KEYS *`) blocks everyone.

**[Distributed Caching](./caching/distributed-caching.mdx)**

- **Local cache:** fastest, but every server has its own copy. Use for tiny, hot data with a short TTL.
- **Shared cache** (Redis): one copy for all servers. The usual choice.
- **Sharding** spreads keys over many cache servers by hashing the key.
- `hash mod N` moves **most keys** when N changes. Use **consistent hashing** (a ring) or **hash slots** (Redis Cluster).
- **Replicas** keep a copy of each shard. **Failover** promotes the replica when the primary dies.
- **Redis Cluster:** data types, built-in sharding (16,384 slots) and failover. **Memcached:** simple and multi-threaded, no replicas.

**[Cache Problems](./caching/cache-problems.mdx)**

- All four problems = the cache stops helping, and the **database gets flooded**.
- **Stampede:** a hot key expires. Fix with a **lock** (one reloader), **early refresh**, **TTL jitter**.
- **Penetration:** requests for data that doesn't exist. **Cache "not found"**, use a **Bloom filter**.
- **Hot key:** one key overloads one shard. **Local cache** or **several copies** of the key.
- **Cold start:** empty cache. **Warm it up** and **shift traffic slowly**.

**[CDN and Edge Caching](./caching/cdn.mdx)**

- A **CDN** keeps copies of files on **edge servers** near users. The real files live on the **origin**.
- Edge **hit** = fast, near the user. **Miss** = fetch once from the origin, then keep a copy.
- Put **static files, images, video chunks** and **public** API responses on a CDN. Personal responses (like `/api/me`) are `private`. Private files use **signed URLs**.
- `Cache-Control` decides how long: `max-age` (everyone), `s-maxage` (CDN only), `private`, `no-store`.
- **Versioned file names** (`app.3f9a1c.js`): cache for a year, and change instantly with a new name.
- Even **1-2 seconds** of edge caching can remove most of the load from the origin.

## 5. Messaging and Events

**[Sync vs Async Communication](./messaging/sync-vs-async.mdx)**

- **Sync** = phone call: wait for the answer. Simple, but delays and failures **add up** along a chain.
- **Async** = voice message: put a message in a **queue** and move on. A worker does it later.
- Async survives a **down** service and soaks up **spikes**, but it is harder to debug and data catches up **later**.
- Rule: **sync** for what the user must know now, **async** for everything after.
- Slow work (emails, videos, PDFs) is async. APIs answer `202 Accepted` for it.

**[Message Queues and Pub/Sub](./messaging/message-queues-pub-sub.mdx)**

- **Producer** sends, **consumer** handles, the **broker** stores messages in between.
- **Queue** = each message to **one** consumer. Add workers to go faster.
- **Pub/sub** = every subscriber gets a **copy**. Add subscribers to add features.
- Real systems mix them: a topic **fans out** to one queue per service.
- Queues **soak up spikes**, **survive failures** and let each side **scale alone**.
- Watch **queue length** and **age of the oldest message**.

**[Event-Driven Architecture](./messaging/event-driven-architecture.mdx)**

- An **event** is a **fact** in the past tense: `OrderPlaced`. It can't be changed.
- A **command** says "do this" to one receiver. An **event** says "this happened" to anyone listening.
- The publisher doesn't know its consumers, so adding a feature = **adding a subscriber**.
- Good: loose coupling, easy to extend. Bad: hard to trace, data **catches up later**, duplicates.
- Use a **correlation ID** to follow one order across services.
- Failures across steps → [Saga](./distributed-systems/saga-pattern.mdx). Safe publishing → [Outbox](./distributed-systems/outbox-pattern.mdx).

**[Kafka](./messaging/kafka.mdx)**

- Kafka is a **log**: messages are added at the end and **stay** after being read.
- A **topic** is split into **partitions**. The **offset** is a message's position in a partition.
- Consumers **commit** their offset. A crash before the commit means the message is read **again**.
- Every **consumer group** gets every message. Inside a group, partitions are **split** between consumers.
- Order is kept **only inside a partition**, so use a **key** (like the order ID).
- Fast because of **append-only writes, page cache, zero-copy, batching** and **partitions**.

**[Kafka vs RabbitMQ vs SQS](./messaging/kafka-vs-rabbitmq-vs-sqs.mdx)**

- **Kafka** = a log. Messages **stay**, many groups read, you can **replay**. Huge throughput, harder to run.
- **RabbitMQ** = a smart broker. **Exchanges** route by rules. Deleted after **ack**. Priorities and routing.
- **SQS** = a simple **managed** queue. **Visibility timeout**, Standard vs **FIFO**, add **SNS** for fan-out.
- Replay or many readers → **Kafka**. Smart routing → **RabbitMQ**. Simple jobs on AWS → **SQS**.
- Using two of them together is normal.

**[Delivery Guarantees](./messaging/delivery-guarantees.mdx)**

- **At-most-once:** ack first. May **lose** messages, never doubles. OK for metrics.
- **At-least-once:** work first, then ack. Never loses, may **double**. The normal choice.
- Exactly-once **delivery** is impossible over a network. Exactly-once **processing** is possible.
- **Exactly-once processing = at-least-once + idempotent consumer.**
- Kafka exactly-once works only **inside Kafka**. Emails and card charges still need idempotency.

**[Idempotency](./messaging/idempotency.mdx)**

- **Idempotent** = once or many times, **same effect**. It makes retries safe.
- The **client** makes one **idempotency key** per action. Every retry sends the same key.
- The server saves key + answer. A repeat gets the **saved answer**, and the work is not done again.
- Claim the key **atomically** (unique constraint), so two copies can't both win.
- For messages, the **event ID** is the key. Save it in the **same transaction** as the work.
- Store keys in the **same database** as the data. Keep them about **24 hours**.

**[Retries, Backoff and Timeouts](./messaging/retries-backoff-timeouts.mdx)**

- **Every** network call needs a **timeout**. A stuck call without one can take down the caller.
- Retry **timeouts, 5xx and 429**. Don't retry other **4xx**.
- Only retry what is **safe to repeat**. Use an **idempotency key**.
- **Exponential backoff:** 100 ms, 200, 400, 800... up to a **cap**.
- **Jitter** = random waits, so clients don't retry in **waves**.
- Retry at **one layer**, limit the tries, and use a **circuit breaker** when a service keeps failing.

**[Dead-Letter Queues](./messaging/dead-letter-queues.mdx)**

- A **poison message** fails every time. Without a DLQ, it is retried **forever** and can block others.
- A **DLQ** takes a message after **N failed tries**, so the main queue keeps flowing.
- Retry **short-lived** errors with backoff. Send **permanent** errors to the DLQ.
- Retry topics and the DLQ **break per-key order**. If order matters, park the **whole key** or pause the partition.
- **Alert** when the DLQ is not empty. Fix the cause, then **replay** (redrive).
- Replay is only safe if consumers are **idempotent**.

**[Eventual Consistency in Async Systems](./messaging/eventual-consistency-async.mdx)**

- Async = the change is saved in **one place first**, and copies **catch up later**.
- The delay is **lag**: usually seconds, but minutes if a consumer is slow or down. Watch **consumer lag**.
- Hide it: **return the result**, **optimistic UI**, **"pending" state**, **push** the update.
- **Read-your-own-writes:** the writer always sees their own change. Read from the source for a short while.
- Money, the last seat and unique names must be **strongly consistent**. The rest can be eventual.

## 6. Distributed Systems

**[Why Distributed Systems Are Hard](./distributed-systems/why-distributed-is-hard.mdx)**

- A **distributed system** = many machines that talk over a network and act as one.
- Messages can be **lost, late, duplicated or out of order**.
- **No reply tells you nothing.** Slow looks the same as dead.
- **Partial failures:** some parts work while others fail, leaving work half done.
- **No shared clock.** Don't trust timestamps across machines.
- Fix with **timeouts, retries + idempotency, copies of data**, and patterns like **sagas** and the **outbox**.

**[CAP Theorem](./distributed-systems/cap-theorem.mdx)**

- **C** = newest data, **A** = always an answer, **P** = survives network breaks.
- Network breaks always happen, so the real choice is **C or A**.
- Ask: "Is old data worse, or is an error worse?"
- **Money and bookings → consistency.** Likes, feeds, profiles → availability.
- Availability usually comes with **eventual consistency**.
- You can choose **per feature**.
- **PACELC:** if **P**artition, pick **A** or **C**. **E**lse, pick **L**atency or **C**onsistency, because syncing copies costs time on **every** write.

**[Consistency Models](./distributed-systems/consistency-models.mdx)**

- A **consistency model** = what a reader may see while copies catch up.
- **Strong:** always the latest. Slower, and fails during network problems.
- **Eventual:** copies agree soon. Fast and always up, but reads can be old.
- **Read-your-writes:** users always see their own changes. Read from the primary right after a write.
- **Quorum:** if **R + W is greater than N**, reads see the latest finished write. Close to strong, but not fully strong.
- Ask **"what breaks if this is a few seconds old?"** and choose **per feature**.

**[ACID vs BASE](./distributed-systems/acid-vs-base.mdx)**

- **ACID** = correct first: all-or-nothing, rules kept, saved for good.
- **BASE** = available first: always answers, copies agree **eventually**.
- When the network breaks, a single-primary SQL setup usually picks CAP's **C**. BASE picks **A**. (ACID itself says nothing about copies.)
- ACID's C (rules kept) is **not** CAP's C (newest data for every reader).
- **Money, orders, bookings, stock → ACID.** Likes, feeds, logs → BASE.
- Most databases now offer **both**, per operation. Choose on purpose.
- Start with ACID unless scale forces you away from it.

**[Distributed Transactions and 2PC](./distributed-systems/distributed-transactions-2pc.mdx)**

- A **distributed transaction** = all-or-nothing across many databases.
- **2PC:** phase 1 **prepare** (everyone votes), phase 2 **commit or abort** (one decision for all).
- A "yes" vote is a **promise**: the participant keeps its locks and waits.
- Big weakness: if the **coordinator dies**, participants are **stuck** holding locks.
- Also slow, and everyone must be up and must support 2PC.
- Between microservices, use a **saga** instead. 2PC lives on inside databases like **Spanner**.

**[Saga Pattern](./distributed-systems/saga-pattern.mdx)**

- A **saga** = a long flow split into local steps that each **commit right away**.
- If a step fails, run **compensating actions** (undo steps) for earlier steps, in **reverse order**.
- Undo is a **new action** (refund), not an eraser. It must be **idempotent** and retried until it works.
- Add each undo **before** its step runs, even for the last step: a lost reply doesn't mean it failed.
- Put steps that **can't be undone** (emails, shipping) **last**, and retry them until they work.
- **Choreography** = services react to events. **Orchestration** = one conductor. Orchestration is easier to follow.
- Tools: **Temporal**, AWS Step Functions, Conductor OSS (first built at Netflix).

**[Outbox Pattern](./distributed-systems/outbox-pattern.mdx)**

- **Dual write problem:** saving to the database and sending to a queue can't be one transaction.
- **Outbox:** write the event into an `outbox` table in the **same transaction** as the data.
- A **relay** reads the outbox and publishes to Kafka, by **polling** or by reading the log (**CDC**).
- Result: **at-least-once delivery**. Events are never lost, but can arrive **twice**.
- Consumers must be **idempotent**: skip event IDs they've already seen.

**[Change Data Capture (CDC)](./distributed-systems/change-data-capture.mdx)**

- **CDC** = turn every insert, update and delete into an event.
- Best way: **read the database's log** (PostgreSQL WAL, MySQL binlog).
- The app writes to **one place**. Search, caches and analytics **follow the log**.
- Avoids the **dual write problem**. Copies lag a little: **eventual consistency**.
- Events can repeat, so consumers **upsert by ID**.
- Tool to name: **Debezium**, with Kafka.

**[Distributed Locking](./distributed-systems/distributed-locking.mdx)**

- A **distributed lock** lives in a shared place (Redis, etcd, ZooKeeper), so all servers see it.
- Redis: `SET key token NX PX 30000`. Release **only if the token is still yours**.
- Locks must **expire** (a **lease**), or a crashed holder blocks everyone forever.
- A paused holder can **wake up after its lease expired** and still think it has the lock.
- **Fencing tokens:** an always-increasing number. Storage **rejects old tokens**.
- Redis locks for **saving work**. etcd/ZooKeeper + fencing for **correctness**.
- Fencing can't stop side effects like a second email. Make the work **idempotent** too: one invoice per customer per month.

**[Leader Election and Consensus](./distributed-systems/leader-election-consensus.mdx)**

- **Leader election:** servers pick one leader. **Consensus:** servers agree on the same data.
- A **majority** (quorum) is needed. Two majorities always overlap, so there is **one leader**.
- Use **3 or 5** servers. 3 can lose 1, 5 can lose 2.
- **Raft:** leader, followers, numbered **terms**, heartbeats, majority votes.
- **Split brain** = two leaders. Prevent it with majorities, terms and fencing.
- In practice, use **etcd** or **ZooKeeper**. Don't build your own.

**[Clocks: Physical, Logical and Vector](./distributed-systems/clocks.mdx)**

- Every server's clock **drifts**. Timestamps from different servers can be in the **wrong order**.
- **Last write wins** with bad clocks can silently **lose** newer writes.
- Use a **monotonic clock** to measure durations. The wall clock can jump back.
- **NTP** keeps clocks close (milliseconds), never perfect.
- **Lamport clock:** a counter. If X caused Y, X's number is smaller.
- **Vector clock:** one counter per server. Can spot **concurrent** writes (conflicts).

**[Distributed ID Generation](./distributed-systems/distributed-id-generation.mdx)**

- **Auto-increment** is perfect on one database, but breaks with **sharding**.
- **UUID:** 128 bits, no coordination. v4 is random; **v7 is sorted by time**.
- **Snowflake:** 64 bits = **1 sign + 41 time + 10 machine + 12 sequence**.
- Snowflake IDs are made locally, are **sorted by time**, and allow 4,096 per ms per server.
- **Counter ranges:** each server takes a **block** of numbers. Great for short codes.
- Send 64-bit IDs to JavaScript clients as **strings**.

**[CQRS](./distributed-systems/cqrs.mdx)**

- **CQRS** = one model for **commands** (writes), another for **queries** (reads).
- The read model is **ready-made** for the screen. No joins at read time.
- Keep them in sync with **events** (outbox), **CDC**, or **event sourcing**.
- The read side **lags**: eventual consistency. Show the user's own change from the response.
- Projectors must be **idempotent**. Views can be **rebuilt** from events.
- Not for simple CRUD. Use it only where reads and writes really differ.

**[Event Sourcing](./distributed-systems/event-sourcing.mdx)**

- **Event sourcing** = store every change as an **event**. Never change or delete events.
- Current state = **replay** the events, like adding up a bank passbook.
- **Snapshots** save the state every N events, so replays stay fast.
- Usually paired with **CQRS**: read views are built from the events.
- Good: **full history, audit, time travel**. Bad: complex, versioning, hard to delete data.
- Use it for **money, ledgers and audit trails**, not for simple CRUD.

## 7. Reliability and Security

**[Redundancy and Failover](./reliability-security/redundancy-failover.mdx)**

- A **single point of failure** takes everything down. Ask "what if this dies?" for every box.
- **Redundancy** = spares at every layer: load balancer, app servers, database, zone.
- **Active-passive:** the spare waits. **Active-active:** all copies work and share the load.
- **Failover** = detect, decide, promote, redirect, fence the old one.
- Watch out for **split brain** and **lost writes** with async replication.
- **Test failover regularly.** An untested spare often doesn't work.

**[Circuit Breaker](./reliability-security/circuit-breaker.mdx)**

- One slow service can use up all of its callers' threads: a **cascading failure**.
- **Closed** = normal. **Open** = fail fast, don't call. **Half-open** = let a few test calls through.
- It opens on a **failure rate** (errors and timeouts), and closes when the test calls succeed.
- Always pair it with a **fallback**: cached data, a default, or hide the feature.
- Use it with **timeouts**, **retries with backoff** (the retry wraps the breaker) and **bulkheads**.
- Tools: **Resilience4j**, Polly, opossum, or a service mesh like Istio.

**[Bulkhead Pattern](./reliability-security/bulkhead.mdx)**

- Named after the walls in a ship that stop one leak from sinking it.
- Give each dependency its **own pool** of threads or connections.
- When a pool is full, **fail fast** and use a fallback. Don't wait.
- It works at every size: threads, connection pools, queues, server groups, **cells**.
- Pair it with a **circuit breaker**: the bulkhead limits the damage, the breaker stops the calls.

**[Rate Limiting](./reliability-security/rate-limiting.mdx)**

- Rate limiting protects against overload and abuse, and keeps things fair. Return **429** with `Retry-After`.
- **Token bucket:** tokens refill at a steady rate, bursts are fine up to the bucket size. The usual default.
- **Leaky bucket:** a queue emptied at a fixed speed, so the output is smooth.
- **Fixed window:** one counter per minute. Simple, but allows **2× bursts** at the window edges.
- **Sliding window log** is exact but stores every request. **Sliding window counter** is a cheap, close estimate.
- Put it in the **API gateway**, with counters in **Redis** shared by all servers.

**[Backpressure](./reliability-security/backpressure.mdx)**

- **Backpressure** = the slow part tells the fast part to slow down.
- An **unlimited queue** only hides overload. The delay grows, then memory runs out.
- **Every queue needs a limit**, and a plan for when it is full.
- Three ways: **reject** (503 or 429), **slow down** the sender (blocking, pull, credits), or **drop** (only when losing data is OK).
- Watch **queue length** and **consumer lag**.
- Rate limiting is a fixed rule per user. Backpressure reacts to load right now.

**[Graceful Degradation](./reliability-security/graceful-degradation.mdx)**

- Keep the **core job** working. Switch off or simplify the rest.
- Decide **in advance** what is critical, and what each fallback is.
- Fallbacks: **stale cache**, **default data**, **hide the feature**, **read-only mode**.
- **Feature flags** and **kill switches** turn features off in seconds, without a deploy.
- Never fake critical results like payments. Tell users when data may be old.
- **Test the fallback path**, or it won't work when you need it.

**[Disaster Recovery: RPO and RTO](./reliability-security/disaster-recovery.mdx)**

- **RPO** = how much data you can lose. It sets how often you copy data.
- **RTO** = how long you can be down. It sets how ready the spare must be.
- Lower RPO and RTO cost more. Choose based on what downtime and lost data cost.
- **Replication is not a backup**: it copies mistakes too. Keep point-in-time backups.
- Keep backups in **another region** and **another account**, locked against deletes.
- Strategies: backup and restore, pilot light, warm standby, active-active.
- **Practice restores and failovers.** An untested backup is only a hope.

**[Authentication vs Authorization](./reliability-security/authn-vs-authz.mdx)**

- **Authentication** = who are you (`401`). **Authorization** = what can you do (`403`).
- Authentication comes first: password and MFA, then a session or token on each request.
- Check **authentication at the gateway**. Check detailed **authorization in the service** that owns the data.
- Always check that the user may access **this exact object** (IDOR / BOLA).
- Take the user ID from the checked token, never from the request body or URL. Hiding a button is not security.

**[OAuth 2.0 and OpenID Connect](./reliability-security/oauth-oidc.mdx)**

- **OAuth 2.0** = limited access to your data that you can take back, without sharing your password. A valet key.
- **OIDC** = OAuth + login. It adds the **ID token**, a JWT that says who you are.
- **Authorization code flow:** go to the provider, user clicks Allow, a code comes back, the server swaps the code for tokens.
- Use **PKCE** for every app, and `state` to block CSRF.
- **Access token:** short-lived, sent to the API. **Refresh token:** long-lived, kept safe, gets new access tokens.
- Check the ID token's signature, `iss`, `aud` and `exp`. Identify the user by `sub`.

**[Role-Based Access Control (RBAC)](./reliability-security/rbac.mdx)**

- **Permissions go to roles, roles go to users.**
- Check **permissions** in code, not role names.
- Roles are often given **per team or project**, not for the whole app.
- Give the **least privilege** needed, and watch for **role explosion**.
- **ABAC** uses facts (owner, time, department) for detailed rules. Most apps mix RBAC with ownership checks.

**[Encryption at Rest and in Transit](./reliability-security/encryption.mdx)**

- **In transit = TLS** everywhere: HTTPS for users, **mTLS** between services, TLS to databases.
- **At rest:** disk, database and S3 encryption protect stolen files, not a hacked app. Add **field-level** encryption for the most sensitive data.
- Keys live in a **KMS**, never in code or next to the data.
- **Envelope encryption:** a data key locks the data, and the master key locks the data key.
- **Passwords: hash, never encrypt.** Use bcrypt or Argon2, with a **salt**.
- Symmetric (AES) is fast. Asymmetric (public and private keys) is used to agree on keys.

**[API Security Basics](./reliability-security/api-security.mdx)**

- **Never trust the client.** Check type, range, format and size on the server, with an allowlist.
- **SQL injection:** use parameterized queries. **XSS:** escape output, add CSP, use HttpOnly cookies.
- Accept and return **only the fields you list**.
- **Rate limit** logins, expensive calls and business flows. Cap page sizes.
- **Secrets** go in a secrets manager, never in git. Give least privilege and rotate.
- OWASP API risk number 1 is **BOLA**: always check the user may access this exact object.

**[CSRF and CORS](./reliability-security/csrf-cors.mdx)**

- **Origin** = scheme + host + port. Pages can **send** requests to other origins, but can't **read** the responses unless the server allows it.
- **CSRF:** another site makes the user's browser send a request, and the browser adds the user's cookies by itself.
- CSRF defenses: **`SameSite` cookies**, **CSRF tokens**, an **`Origin` check**, and **no data changes with `GET`**.
- `Authorization: Bearer` tokens aren't sent automatically, so no CSRF. But scripts can read them, so watch for **XSS**.
- **CORS:** the server says which origins may **read** its responses. Non-simple requests get an `OPTIONS` **preflight** first.
- With credentials, `Access-Control-Allow-Origin` must be an **exact origin**, never `*`. Never echo back whatever `Origin` arrives.
- **CORS protects users' data in the browser, not your server**, and it does **not** stop CSRF.

## 8. Advanced Components

**[Object, Block and File Storage](./advanced-components/storage-types.mdx)**

- **Block** = raw disk for one server. Fastest. Use it for **databases**.
- **File** = shared network folder (NFS). Use it when many servers need **the same folder**.
- **Object** = flat bucket of objects with keys, over **HTTP**. Cheap and almost unlimited. Use it for **photos, videos, backups, logs**.
- You **can't edit part of an object**. You replace the whole thing.
- Never store big files in the database. Store them in **S3** and keep the **key** in the database.
- AWS names: **EBS** (block), **EFS** (file), **S3** (object).

**[Search and Inverted Indexes](./advanced-components/search.mdx)**

- `LIKE '%word%'` reads every row. Search engines use an **inverted index**: **word → list of documents**.
- The **analyzer** lowercases, splits into words, and cuts words to their root, on both documents and queries.
- **Ranking:** frequent in this doc, rare overall, short field = better match. Elasticsearch uses **BM25**.
- Elasticsearch splits an index into **shards** and asks all of them (**scatter-gather**).
- Search is a **copy**. The database stays the source of truth.
- Keep them in sync with **CDC + Kafka**. Search is a second or so behind.

**[Elasticsearch](./advanced-components/elasticsearch.mdx)**

- An index is split into **primary shards** (fixed when you create it) with **replicas** on other nodes.
- **`text`** fields are analyzed for full-text search. **`keyword`** fields are exact, for filters, sorting and counts.
- Search is **near real time**: a **refresh**, about once a second, makes new documents searchable. Get by ID is instant.
- A search is **scatter-gather** in two phases: **query** (IDs and scores from every shard), then **fetch** (full documents for the winners). Deep pages are costly: use `search_after`.
- Words go in **`must`** (scored). Everything else goes in **`filter`** (yes or no, cached).
- It is **not the source of truth**. Feed it with **CDC or the outbox**, use the database ID as the document ID, and rebuild with an **alias** swap.

**[Geospatial Indexing](./advanced-components/geospatial-indexing.mdx)**

- A normal index sorts one value. A location has **two**, so it can't find "near me" fast.
- **Geohash** turns a location into a string. **Longer = smaller square. Same prefix = same square.**
- Pick a cell **at least as big as the search radius** (5 characters for 2 km). Search **your cell + its 8 neighbors**, then filter and sort by real distance.
- **Quadtree** splits crowded squares into 4. Good for **uneven density**.
- Tools: **Redis GEO** for moving drivers, **PostGIS** or **Elasticsearch** for places.
- Uber uses hexagons (**H3**). Google uses **S2** cells.

**[Bloom Filter, HyperLogLog, Count-Min Sketch](./advanced-components/probabilistic-data-structures.mdx)**

- Trade a **small error** for **tiny memory** and high speed.
- **Bloom filter:** "seen it?" Answers **"definitely not"** or **"maybe"**. No false negatives. Can't delete.
- **HyperLogLog:** counts **unique** items in about **12 KB**, about 1% off. Idea: the longest run of leading zeros.
- **Count-Min Sketch:** "how many times?" Take the **smallest** counter. Can be too high, never too low.
- Classic uses: Bloom filters in **Cassandra** reads and **crawlers**, HyperLogLog for **unique views**, Count-Min Sketch for **trending**.

**[Batch vs Stream Processing](./advanced-components/batch-vs-stream.mdx)**

- **Batch** = big chunk, on a schedule, results later. Simple, cheap, easy to rerun. Tool: **Spark**.
- **Stream** = each event right away. Fresh results, but harder. Tool: **Flink** (or Kafka Streams), reading from **Kafka**.
- Choose by asking: **"How fresh must the answer be?"**
- Streams are counted in **windows**: **tumbling** (no overlap), **sliding** (overlap), **session** (per visit).
- **Event time** vs **processing time**. A **watermark** decides when to close a window.
- Fast numbers from stream, exact numbers from batch = **Lambda**. Stream only, replay to fix = **Kappa**.

**[Hot Keys, Hot Partitions and Fan-out](./advanced-components/hot-keys-fan-out.mdx)**

- **Hot key** = one key with far more traffic. **Hot partition** = the one machine holding it.
- Spot them by comparing shards, counting requests per key, or the database's own tools (like `redis-cli --hotkeys`).
- Read fixes: **cache, in-memory copy, key copies, CDN, combine identical requests**.
- Write fixes: **split the counter** into sub-keys, **buffer and batch** writes.
- **Fan-out on write** (push): fast reads, heavy posting. **Fan-out on read** (pull): cheap posting, slow reads.
- **Celebrity problem:** pushing to millions of feeds is too slow. Use a **hybrid**: push for normal users, pull for celebrities.

**[API Pagination and Versioning](./advanced-components/api-pagination-versioning.mdx)**

- Always paginate lists, and cap the page size.
- **Offset** (`LIMIT 20 OFFSET 40`): simple, can jump to a page, but **slow when deep** and shows **duplicates** when data changes.
- **Cursor**: "after this item". `WHERE (created_at, id) < (...)` with an index. **Fast and stable.** Default for feeds.
- Make the cursor **opaque** and add the **ID as a tie-breaker**.
- Version in the **URL** (`/v1/`) or a **header**. Keep old versions running until traffic is gone.
- **Adding optional things is safe. Removing, renaming or changing types breaks clients.**

**[File Upload and Download](./advanced-components/file-upload-download.mdx)**

- **Don't send big files through app servers.** It wastes them and hits size and time limits.
- **Presigned URL** = a signed, short-lived link to upload or download **one** object directly from S3.
- Save a **metadata row** (`pending`), upload, then mark it **ready** when S3's event arrives. A **sweeper** cleans up rows stuck in `pending`.
- Big files: **multipart upload**. Parts in parallel, retry only failed parts, **resume** after a crash.
- Downloads: **CDN** for public files, **signed URLs** for private ones, **range requests** to resume and seek.

**[Background Jobs and Job Scheduling](./advanced-components/background-jobs.mdx)**

- If the user doesn't need it **now**, put it on a **job queue** and let **workers** do it.
- Jobs carry **IDs**, not whole objects. A crashed worker's job comes back, so jobs must be **idempotent**.
- A crash between saving the data and queuing the job loses the job. Use an **outbox**, or a **sweeper** that re-queues old `pending` rows.
- Cron on every server runs a job **many times**. Use **one scheduler** or a **lock**.
- Many "run at" jobs: rows with `run_at`, claimed with `UPDATE … SKIP LOCKED … RETURNING`.
- Long jobs: return **`202 Accepted` + job ID**, and let the client check the status.
- **Retry with backoff**, cap the tries, then send to a **dead-letter queue**.

**[Multi-tenancy](./advanced-components/multi-tenancy.mdx)**

- **Tenant** = one customer organization. **Multi-tenant** = one system serves all of them.
- Three models: **shared tables** (`tenant_id`, cheapest), **schema per tenant**, **database per tenant** (safest, costliest). Most systems **mix** them.
- Take the tenant ID from the **login token**, never from the request.
- Protect in layers: shared query filter, **Row-Level Security**, tenant ID in **cache keys and file paths**.
- **Noisy neighbors:** per-tenant rate limits, fair queues, move big tenants to their **own shard**.

**[Microservices in Practice](./advanced-components/microservices-patterns.mdx)**

- **Sync** when you need the answer now. **Async** (events) to tell others something happened.
- Long sync chains are slow and fragile. Use **timeouts, retries and circuit breakers**.
- **Split by business area**, not by technical layer. One team owns each service.
- **Each service owns its data.** No shared database. Copying some data is normal.
- Cross-service transactions: **saga** + **outbox**.
- Watch for the **distributed monolith**, too-small services and chatty calls.

**[Strangler Pattern](./advanced-components/strangler-pattern.mdx)**

- **Big-bang rewrites** are risky: moving target, no feedback, lost rules, one huge switch day.
- **Strangler:** put a **routing layer** in front, move **one feature at a time**, then delete the old part.
- Move traffic **slowly** (1%, 10%, 100%) and keep a way to **switch back**.
- Start with **low-risk, read-only** features. Do money flows last.
- Keep data in sync during the move, for example with **CDC**.

## 9. Production Systems

**[Observability: Logs, Metrics, Traces](./production/observability.mdx)**

- **Metrics** tell you **something is wrong**. **Traces** tell you **where**. **Logs** tell you **why**.
- Write **structured (JSON) logs** with a **trace ID**. Never log secrets.
- Metric types: **counter** (only up), **gauge** (up and down), **histogram** (spread, for percentiles).
- **Four golden signals:** latency, traffic, errors, saturation.
- A **trace** = one request's journey. A **span** = one step. The ID travels in the `traceparent` header.
- **OpenTelemetry** = one standard for all three, sent to any tool.

**[Latency Percentiles: p50, p95, p99](./production/latency-percentiles.mdx)**

- The **average lies**: one slow request pulls it up, and it describes nobody.
- **Sort, then pick:** p90 = the value 90% of the way down the sorted list.
- **p50** = typical. **p95** = 1 in 20 slower. **p99** = 1 in 100 slower, the **tail**.
- **Fan-out** makes the tail worse: 100 servers at 1% slow each = **63%** of requests slow.
- **Alert on p99 or p95 over a window**, per important endpoint, next to the error rate.
- **Never average percentiles.** Combine histograms, then compute.

**[SLI, SLO and SLA](./production/sli-slo-sla.mdx)**

- **SLI** = what you **measure**: good events / all events.
- **SLO** = your **goal**: SLI + target + time window, like 99.9% over 30 days.
- **SLA** = the **contract** with customers, with a penalty. Looser than the SLO.
- **Error budget** = 100% minus the SLO. Budget left: ship. Budget gone: fix reliability.
- 99.9% over 30 days = about **43 minutes** of downtime. 99.99% = about **4.3 minutes**. 99.999% = about **26 seconds**.
- **Never aim for 100%.**

**[Finding Bottlenecks](./production/finding-bottlenecks.mdx)**

- A **bottleneck** is the narrow part that limits everything. Fixing anything else doesn't help.
- **Measure first:** metrics → trace → resource. Fix the **biggest** part. Change **one** thing. Measure again.
- Look at **CPU, memory, disk, network, the database, and waiting on others**.
- **USE method:** Utilization, Saturation, Errors.
- Database: **slow query log** finds the queries, **EXPLAIN** shows why. `Seq Scan` on a big table = missing index.
- Classic fixes: **index, fix N+1, fetch less, pool connections, cache**.

**[Load Testing](./production/load-testing.mdx)**

- **Load test:** expected peak traffic. **Stress test:** add traffic until it breaks. Also **spike** and **soak** tests.
- Measure **throughput, p95/p99 latency, error rate** and **saturation** of each resource.
- Look for **the knee**: latency starts to climb, throughput stops growing.
- The first resource to fill up at the knee is your **bottleneck**.
- Tools: **k6** (JavaScript), **JMeter** (visual editor), Gatling, Locust.
- Make it **realistic**: production-sized data, many different IDs, mocked third parties.

**[Deployment Strategies](./production/deployment-strategies.mdx)**

- **Rolling:** replace servers a few at a time. No extra servers, slow rollback, two versions live.
- **Blue-green:** two full copies, switch all traffic at once. **Instant rollback**, double the servers.
- **Canary:** a small share of users first, watch metrics, then grow. **The safest.**
- **Feature flags** separate deploying code from releasing a feature. Turn off in seconds.
- Database changes: **expand and contract**, so old and new code both work.
- Make rollback **one command, or automatic**.

**[CI/CD, Docker and Kubernetes](./production/cicd-docker-kubernetes.mdx)**

- **CI:** build and test every change automatically. **CD:** always ready to deploy, or deployed automatically.
- **Docker image** = the packed box. **Container** = a running copy of it.
- Kubernetes: **pod** (running container), **deployment** (keeps N pods), **service** (stable address + load balancing).
- **HPA** adds and removes pods with load. For CPU, the pods need **CPU requests** set. Crashed pods are **replaced automatically**.

## 10. Interview Questions

**[Design a URL Shortener](./questions/url-shortener.mdx)**

- **Read-heavy** → add a cache.
- **Unique codes** → counter + base62. 7 characters = about 3.5 trillion codes. Custom aliases can take a future
  counter code, so the insert must fail on a taken code.
- **302** if you need expiry or analytics. **301** is faster, but browsers remember it.
- **Stateless services** behind a load balancer. Scale reads and writes separately.
- 1 billion links × 500 bytes = **500 GB**. No need to split the database at first.

**[Design a Rate Limiter](./questions/rate-limiter.mdx)**

- Put the limiter in the **API gateway**: one place, every request.
- **Token bucket:** short bursts allowed, average rate kept, only two numbers per client.
- Shared counters in **Redis**. Read and update in **one atomic step** (a Lua script, or `INCR` + `EXPIRE` inside
  `MULTI`/`EXEC`).
- In Redis Cluster, use a **hash tag** like `rate:{user-42}:search`, so one client's keys sit on one server.
- Return **429** + `Retry-After`. Clients back off with jitter.
- If Redis is down, usually **fail open**.
- 100 million users × 100 bytes = 10 GB. Memory is easy; **requests per second** is the hard part.

**[Design a Notification Service](./questions/notification-service.mdx)**

- Callers get **202 Accepted**. The real sending happens later, from a **queue**.
- **Separate queues per channel and priority**, so login codes never wait behind marketing.
- **Retry with backoff + jitter**, then send to a **dead-letter queue**.
- One **delivery** row per notification and channel, each with its own status.
- Save first, then queue. A **scheduler** puts missed deliveries (empty `enqueued_at`) on the queue (the outbox idea).
- Every status change is a **conditional update**, so a late update can't undo a newer one. Provider webhooks are
  **signed** and de-duplicated by event ID.
- **Two dedupe checks:** idempotency key at the API, and a **claim** (one conditional update) in the worker.
- Exactly-once is impossible. Make duplicates **rare**.
- Respect users: **settings, frequency caps, quiet hours**.

**[Design WhatsApp](./questions/whatsapp.mdx)**

- **WebSockets** let the server push messages to phones at any time.
- **Save first, then ack.** One tick = safe in the database.
- Every message gets an **inbox** row, deleted on the `delivered` receipt. A push notification wakes offline phones.
- Route between chat servers with **sharded Redis Pub/Sub, one channel per user**. The database stays the source of
  truth. On connect: subscribe first, then read the inbox.
- The phone retries with the same **clientMsgId**. A dedupe table `(sender, clientMsgId) → messageId` returns the
  first ID, so a retry never makes a second copy.
- No presence key in Redis → the user is offline → send a push notification.
- Store messages by **chatId**, sorted by a time-ordered message ID.
- Receipts are tiny messages. Batch them: "read up to X".

**[Design a News Feed](./questions/news-feed.mdx)**

- Feeds are **read-heavy**, so do the work **at write time** (fan-out on write).
- The feed cache stores **post IDs only**: newest 500, active users only, in a Redis **sorted set** scored by time.
  Raise `zset-max-listpack-entries` to 512, or the feeds take about 10 TB instead of 2 to 3 TB.
- **Celebrities:** don't fan out. Merge their posts **at read time** (the hybrid).
- Page with a **cursor**, not page numbers. Hydrate with a pipeline of `GET`s, not `MGET` (`CROSSSLOT` in a cluster).
- Ranking = **collect candidates → score → filter**.
- Handle deletes and unfollows **lazily, at read time**.

**[Design a Web Crawler](./questions/web-crawler.mdx)**

- **The loop:** take URL → robots.txt → DNS → download → check hash → save → parse → filter → add new links.
- **Politeness:** cache robots.txt. Front queues for priority, a fixed number of **back queues** (one site each),
  and a **heap** of next allowed times (about 1 request per second per site).
- **Same URL:** normalize it, then check a **Bloom filter** (about 12 GB for 10 billion URLs at 1%).
- **Same page:** check a **hash** of the text **before** saving. Save the page under its hash.
- **Mark "seen" last:** add the hash (or the URL) to its "seen" set only **after** the save (or the insert). Then a
  crash repeats harmless work instead of losing a page.
- **No lost work:** URLs stay `to do` in the URL DB until handled, a parse queue with a visibility timeout, raw HTML
  in S3, separate download and parse.
- **Traps:** maximum depth, maximum URL length, page limit per site.
- 10 billion pages in 5 days = **23,000 pages per second**. 1 PB of HTML → **object storage**.

**[Design Search Autocomplete](./questions/search-autocomplete.mdx)**

- A **trie** with the **top 5 saved at every node**: walk a few letters, read a list.
- **Build offline, then swap** the new trie in memory. Don't update it on every search.
- Rank by **popularity with time decay**. Filter offensive and rare queries.
- A small **trending layer** (a stream job) for fresh trends.
- **Debounce + browser cache + CDN + RAM:** most requests never reach a server. Keep cache times short (1 minute
  in the browser, 5 minutes in the CDN), so a bad suggestion can be removed fast.
- The popular queries are about 3 GB, a few tens of GB with the top 5 lists. That **fits in memory**: make copies,
  don't shard at first.

**[Design a Job Scheduler](./questions/job-scheduler.mdx)**

- Split **Job** (what and when) from **Execution** (one run). Index executions by `runAt`.
- `POST /jobs` takes an **Idempotency-Key**.
- A run due within 5 minutes when it is created (a new job, or the next cron run) is saved as `queued` and goes
  straight to the timer queue, so it is not late and not queued twice. Save first, then queue.
- **Two layers:** the database holds all jobs. A **timer queue** holds the next few minutes.
- Put a **queue** between the scheduler and the workers. Workers pull, and autoscale at busy times.
- Retry with **exponential backoff**, then a **dead-letter queue**.
- Many schedulers share work with `SELECT ... FOR UPDATE SKIP LOCKED`.
- Exactly-once is not possible. **At-least-once + idempotent tasks** = the job takes effect once. Retries keep the
  same `executionId`, so the idempotency key stays the same.

**[Design an E-commerce Platform](./questions/e-commerce.mdx)**

- **Two systems in one:** browsing is read-heavy and can be a bit stale. Checkout must be strictly correct.
- **No overselling:** one atomic `UPDATE ... WHERE available >= 1`. 0 rows changed = sold out, so roll back.
  Update cart items in `product_id` order to avoid deadlocks.
- **Reserve at checkout** with an expiry, and release the stock if payment fails. Before an expired hold is
  released, cancel the payment. If a payment still succeeds late, reserve again or refund.
- **Never charge twice:** save the order first, use **idempotency keys**, and listen for **webhooks**. Check each
  webhook's signature and skip event IDs already handled.
- Card numbers go **straight to the payment provider**, never through our servers.
- The stock shown on the product page can be approximate. The **real check is at checkout**.

**[Design a Ticket Booking System](./questions/ticket-booking.mdx)**

- Booking = **hold** (a few minutes) + **pay**.
- **No double booking:** one atomic update, `WHERE status = 'available' OR the hold has expired`. 0 rows = taken.
- Hold many seats in **one transaction, sorted by seat**, so two buyers can't deadlock.
- Hold and confirm both take an **Idempotency-Key**, inserted first, so a retry never fails on your own hold or
  charges twice.
- Confirm with `status = 'reserved' AND booking_id = 'bk_9'`. Webhooks are signed and de-duplicated by event ID.
- **Expired holds count as free**, so correctness never depends on a cleanup job.
- Never hold a database lock while a human types a card number.
- Seat maps can be a second old. **The truth is the atomic update.**
- **Huge rush → virtual waiting room:** random places, steady admission, signed entry tokens. Look up each place
  once (signed cookie), and share one "admitted so far" number through the CDN.

**[Design Google Drive](./questions/google-drive.mdx)**

- **Bytes in object storage, file info in a database.** Never put big files in a database.
- **Chunks + hashes** give resumable uploads, upload-only-what-changed, and deduplication. Dedupe only inside one account, and check the bytes match the hash.
- **Presigned URLs:** the app talks to storage directly. Our servers only hand out links.
- **Sync = change log + cursor**, plus a **nudge** (long poll or WebSocket) so devices know when to look. The long poll carries the cursor, so no change waits for a lost nudge.
- **Conflicts:** the save sends its `baseVersion`. If it is old, keep both copies. Never lose work silently. A retried `complete` with the same `uploadId` gets `200`, not a conflict.
- Folders point to their **parent by ID**, so renames are cheap.

**[Design Yelp (Nearby Places)](./questions/yelp.mdx)**

- **Read-heavy:** about 1,000 reads for every review written. Optimize for reads.
- Businesses **rarely move**, unlike drivers. Read-friendly geo indexes are fine.
- **Elasticsearch** does text + location + filters in one query. Keep it in sync from Postgres with **CDC**. PostGIS is the simpler choice when the data is small.
- Store **`rating_sum` and `review_count`**, and update them with `+` **in the same transaction** as the review. Never read, change and write back the average.
- **One review per user:** a unique constraint on `(business_id, user_id)`.
- Rank with a **Bayesian average**, so one 5-star review can't beat 2,000 reviews at 4.8.
- Scale reads with **caches** (business pages, popular searches by geohash cell) and **replicas**.

**[Design Instagram](./questions/instagram.mdx)**

- **Photo bytes never go through our API.** Presigned URL → S3. Views come from a **CDN**. Files never change, so they cache for a year.
- **Image workers** make 3 fixed sizes right after upload and **strip GPS** data. The post becomes `ready`, and **only then** fans out.
- **Feed:** fan-out on write for normal users, **merge celebrities at read time**. Details in [Design a News Feed](./questions/news-feed.mdx).
- **Follow graph:** store each follow **twice** (`following` by follower, `followers` by followee), so each question hits one shard.
- **Likes:** the likes table is the truth (`ON CONFLICT DO NOTHING`, so no double counts). Counts are **added up in batches** through Kafka, to avoid a hot row.
- Counts like followers and likes are **stored numbers**, a few seconds behind. Never `COUNT(*)` on a page view.

**[Design Live Comments (Facebook Live)](./questions/live-comments.mdx)**

- Reading is huge, writing is small. **POST** to write, **SSE** to read.
- SSE reconnects by itself and sends **Last-Event-ID**, so catching up is almost free.
- **Save first, then publish.** The database is the truth. Pub/Sub is only the fast path.
- **One Pub/Sub channel per video.** Each realtime server subscribes once per video, not once per viewer.
- A layer-7 load balancer puts **viewers of the same video on the same servers**. Hot videos get many servers.
- **Huge video:** 3,000 comments/s × 10 million viewers is impossible. **Sample** about 10 per second, and send
  **one batch per second**.
- Join: **open the stream first, then load the newest page**, and skip duplicate IDs.
- Older comments: **cursor = last comment ID**, stored by video ID in Cassandra.

**[Design LeetCode (Online Judge)](./questions/leetcode.mdx)**

- **Never trust user code.** Run it in a sandbox: time, memory and process limits, **no network**, read-only files,
  non-root, seccomp. Stronger walls: gVisor or a micro-VM. Judge machines hold no secrets.
- **Expected outputs stay outside** the sandbox. A fresh sandbox for every run.
- Submit returns **202 Accepted**. A **queue** in front of **autoscaled workers**. Scale up **before** a contest.
- **Contest queue first**, practice second. One submission per CPU core, for fair timing.
- A crashed worker's job comes back (**visibility timeout**). Re-running is safe; save the verdict once.
- Results: **poll every second**. Cheap, and the wait is short.
- Leaderboard: **Redis sorted set**. Score = points × 1,000,000 − finish time. `ZADD GT` so scores only go up.
- Cache page 1 of the leaderboard for a couple of seconds.

**[Design Tinder](./questions/tinder.mdx)**

- **Near me + filters** → a search index with a location field (Elasticsearch), **split by area**. Use a
  **two-way filter**: I fit what they want, and they fit what I want.
- Redis GEO fits Uber (only "nearby and free"). Dating needs many filters, and locations change rarely.
- **2 billion swipes a day** (about 70,000 per second at peak) → **Cassandra**, partitioned by swiper.
- **Save, then check** has a race: both can miss the match, or both can create it.
- **Fix:** one record per pair with **sorted IDs** (`likes:asha:ben`). Set my flag and read both flags in **one
  atomic step** (Redis `MULTI`/`EXEC`).
- Matches are keyed by the pair and inserted "only if new", so there is never a second match.
- **Already swiped** → a **Bloom filter** per user. No false negatives, so no repeats. A false positive only hides
  one profile.
- Match alerts go through a **queue** to APNs/FCM, deduped by match ID.

**[Design YouTube](./questions/youtube.mdx)**

- **Bytes never go through our API.** Upload straight to storage, watch straight from the CDN.
- **Multipart parts are joined only when we call `CompleteMultipartUpload`.** The Video Service does it, then marks `processing` and writes a "start" **outbox** row in one transaction, so a crash can't leave the video stuck.
- **Transcode in parallel:** split the video into pieces and give them to many workers.
- **Adaptive bitrate streaming:** small segments + a manifest. The player picks the quality before each segment.
- **HLS** (`.m3u8`) and **MPEG-DASH** (`.mpd`) are the two common standards.
- **CDN is a must:** 10 million viewers × 5 Mbps = 50 Tbps. Segments never change, so they cache well.
- **View counts:** events → Kafka → add up in batches. Avoid one hot database row. Save the Kafka offset in the same transaction, so no batch is added twice.

**[Design Uber](./questions/uber.mdx)**

- **400,000 location updates per second** → keep only the **latest** location, **in memory** (Redis GEO).
- If Redis is lost, the index **refills itself** within about 15 seconds (moving drivers send every 5 s, parked ones every 15 s). Silent for 30 s = ignored.
- **Geohash** turns latitude and longitude into one code. Pick a cell at least as big as the search radius, search the cell **plus its 8 neighbors**, then drop drivers outside the radius.
- Rank nearby drivers by **driving time**, not straight-line distance.
- **No double booking:** a Redis lock with a **10-second TTL** per driver. No answer = the lock expires = next driver.
- **Accept is conditional:** the lock must still hold this ride, the ride must still be `matching`, and the driver must still be `available`.
- **Peaks:** split by city, queue the requests (through an **outbox**, so a saved ride is always queued), and use surge pricing.

**[Design a Payment System](./questions/payment-system.mdx)**

- **Correctness over speed.** About 10 payments per second, so one SQL database is fine.
- **Never touch card numbers.** The PSP gives us a **token**.
- **The server sets the amount** from the order. The browser sends only the order ID.
- **Save PENDING first**, then call the PSP. A timeout means "we don't know yet".
- **Idempotency key end to end:** unique in our database, and passed to the PSP. A retry of a `PENDING` payment calls the PSP again with the same key. If the PSP never got it, the checker marks it `FAILED` after a set time.
- **Webhooks are signed and de-duplicated** by event ID, saved in the same transaction as the status update.
- **Double-entry ledger:** every movement is lines that add up to zero. Append-only. Written only when the status update changed 1 row.
- **Reconciliation** with the PSP every day catches whatever slipped through.

**[Design a Distributed Cache](./questions/distributed-cache.mdx)**

- **Hash map in RAM** per node. About 1 ms per request.
- **`hash % N` moves most keys** when N changes. **Consistent hashing** moves only about 1/N.
- **Virtual nodes** spread keys evenly and share the load when a node dies.
- **Expiry:** check on read, plus a background sampler. **Eviction:** LRU (in Redis, set `allkeys-lru`: the default refuses writes).
- **Primary + replicas**, async copies, **automatic failover by majority vote** in the coordination service. A **lease** makes the old primary stop taking writes before a new one starts.
- A lost `DELETE` = **stale data**, so every key gets a TTL.
- **Hot key** → local cache, copies of the key (update every copy on a change), or read from replicas.

**[Design a Distributed Message Queue](./questions/distributed-message-queue.mdx)**

- **Topic → partitions → append-only log** on disk. Sequential writes are fast.
- **Segments** make deleting old data cheap: delete whole files.
- **Offsets** are per consumer group. Reading never deletes anything.
- **One partition → one consumer per group.** Partitions limit parallelism. Order is only per partition.
- **Commit after processing** = at-least-once. Make consumers idempotent.
- **3 copies, acks = all**, and a new leader is chosen only from in-sync copies.

**[Design a Logging and Metrics System](./questions/logging-metrics.mdx)**

- **Logs = text events. Metrics = numbers over time.** Store them differently.
- **Agent → Kafka → indexers.** Kafka absorbs the spike that comes with every outage.
- **Metrics go in a time-series DB:** compressed blocks, downsampled with age. Keep label cardinality low.
- **Logs go hot → warm → cold**, split by day so deleting is instant.
- **Every search has a time range.** Then full-text index, or labels-only plus a parallel scan.
- **Alerts:** on metrics, with "for 5 minutes", grouped, routed, and watched from outside.

**[Design an Ad Click Aggregator](./questions/ad-click-aggregator.mdx)**

- **Don't count at query time.** Count ahead: one row per ad per minute.
- **Kafka + Flink + 1-minute tumbling windows** for fresh counts. Use **event time** and a watermark.
- **Exactly once** = impression-ID dedupe + checkpoints + "set, not add" writes.
- **Keep raw clicks in S3** and **recount nightly**. Billing uses the recount.
- **Hot ad** → split its key into parts with `hash(impressionId) % 10`, then add the parts. Never a random suffix: it breaks dedupe.
- **Money = exact. Charts can be approximate** (HyperLogLog for unique users).

**[Design Top K (Trending)](./questions/top-k.mdx)**

- **Min-heap of size K** finds the top K without sorting everything.
- **Split by video ID**, keep a local top K per worker, then **merge**. Never split one video's views randomly.
- **Sliding windows:** minute buckets, add the newest, subtract the oldest.
- **Bigger buckets for longer windows:** minutes for an hour, hours for a day.
- **Count-Min Sketch:** fixed memory, never counts too low. Pair it with a heap. For sliding windows: one sketch per bucket, and rebuild the heap every minute.
- **Batch + stream:** the batch gives an exact base with its **cut-off time**, and the merger adds the stream since that cut-off. The merger is the only writer of the lists.
- **Precompute lists into Redis.** Reads never count.

**[Design Google Docs](./questions/google-docs.mdx)**

- **The hard part is edits at the same time**, not scale.
- **Positions shift** when others type. `CAT` example: Bob's "delete 2" must become "delete 3".
- **OT:** a central server orders ops and transforms them. Each browser also transforms incoming ops against its own **pending** ops. Google Docs uses it.
- **One op in flight** per browser, the rest buffered. Then the server never transforms an op against the same browser's earlier ops.
- **CRDT:** characters get fixed IDs, so any order works. Great for offline, uses more memory.
- **One owner server per document**, chosen by consistent hashing on the doc ID. The log only accepts a version once, so two owners can't split the history.
- **Ops log + snapshots:** open = latest snapshot + newer ops. "Saved" only after the log write.
